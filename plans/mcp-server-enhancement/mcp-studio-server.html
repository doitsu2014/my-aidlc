In this design, the MCP server is the assistant-facing entry point, but it is not a shell-shaped proxy to the CLI. The MCP adapter and existing CLI are peers over shared AIDLC operations. Explicit instrumentation in the MCP adapter emits tool-call spans and operation events for MCP callers only; direct CLI use writes no telemetry.

Safety findings · corrections applied

Approver label is not identity

An approval over MCP requires an explicit approved_by label; without one the call is refused (approver_required), and there is no Git or OS username fallback. The label is self-asserted, not authentication; an allowlist only compares a name. Use approval only for a decision the human owner made in this conversation. AI-mode approvals use the existing AI Orchestrator policy, including recommendation and open-item checks; that name is not proof of a person. Host confirmation is an additional UX safeguard only, not server-verifiable authorization. Preserve the resolved name and source when recorded, without presenting either as proof.

Amend plans/mcp-server-detailed-design.md §4.3–4.4 and §10; plans/mcp-server-architecture.md §8–9; implementation plan §3.3 “Gate/approval semantics” and §7 “Risks and mitigations”.

next needs a guard

In MCP v1, require an existing active intent and refuse if none exists; do not expose intent/scope/depth/mode creation or model-controlled force-resume. The existing operation can run owner-configured prerequisite shell checks before selecting a stage, so do not execute them implicitly. Return the configured prerequisite requirement without running it, or add a separately reviewed explicit opt-in. Selection may persist state and audit events. Test active/no-intent and prerequisite cases.

See plans/mcp-server-detailed-design.md §4.3 and §4.4; implementation plan §3.3 tool contract and §4 Phase 2.

Queue preview is not a migration

The existing queue computes a migration preview in memory for legacy unit state and can return migration: pending; it does not persist the migration. Keep it a read tool and state this distinction precisely—do not claim that it migrates or writes state. Test both preview output and unchanged on-disk state.

Amend plans/mcp-server-detailed-design.md §3.3 (the queue tool), §9 “Application parity”; implementation plan §3.3 tool contract and §5 Integration tests.

Audit is not event coverage

Audit records are durable workflow evidence under the existing implementation semantics; telemetry is best-effort operational data. Keep telemetry transition events allowlisted and explicitly partial: list only transitions instrumented in shared code, state that legacy CLI paths can bypass those hooks, and do not imply every state change—or every audit row—has a corresponding telemetry event. Missing telemetry says nothing about whether an operation or gate decision occurred; telemetry never proves approval or replaces audit.

Amend plans/mcp-server-detailed-design.md §6.3 and §7.5; implementation plan §2.4, §3.5, §5 Telemetry and §7 Risks; architecture §7 and §8.

Monitor runs in-process, in the foreground

dtech-aidlc monitor runs the read-only HTTP server inside that command's own process, in the foreground: no daemon, no child process, no browser launch, and no link to the stdio MCP process. It binds 127.0.0.1 only, answers GET only, prints one stderr line with the address and a per-run token in the URL fragment, and stops on Ctrl+C. It is not the MCP transport. Keep CLI command, process lifecycle, packaging, tests, and diagram aligned with that contract.

See plans/mcp-server-detailed-design.md §2 and §7.7; implementation plan §3.2, §3.6, and §4 Phase 4.

Dashboard signal

CLI still stands alone

Setup, administration, shell use, and fallback do not depend on an MCP host.

No second workflow engine

State transitions and policy belong in shared operations, not in a parallel MCP implementation.

Local by default

MCP uses stdio and opens no listener. The dtech-aidlc monitor command serves read-only HTTP on loopback in its own foreground process; the project owns its state.

Audit is not telemetry

The existing append-only audit log records workflow audit events. Bounded, best-effort telemetry is separate and never authorizes writes.

Loopback still needs defenses

Loopback is not process isolation. The monitor checks Host and Origin, sends no CORS headers, and requires a per-run 128-bit token delivered in the URL fragment and sent as a bearer header; the page strips it from the address before the first request.

Telemetry defaults are set

MCP telemetry is on by default; --telemetry off records nothing; the CLI writes none. Retention: each file at most 5 MiB, files older than 7 days deleted, then oldest files until the folder is under 50 MiB. Metadata spans are operational signals, not OpenTelemetry export or proof of an audited gate decision; file integrity and completeness also need separate treatment if stronger assurance is required.

Use honest empty states

No telemetry files cannot distinguish disabled collection from a first run. Show status unknown unless the monitor has a reliable collector-status signal.
