MCP STDIO · NO MCP LISTENER

Keep the engine. Add a new door.

In this proposed design, the MCP server is the assistant-facing entry point, but it is not a shell-shaped proxy to the CLI. The MCP adapter and existing CLI are peers over shared AIDLC operations. Explicit instrumentation could emit MCP tool-call spans and shared-layer workflow events; direct CLI use would get operation-level events only where the CLI route passes through instrumented shared operations, not MCP-level spans.

A deliberately small tool surface

aidlc_statusread

Current intent, stage, gate, and work-unit state.

aidlc_nextstate-affecting

Select the next directive using existing rules; selection may persist workflow state and audit events.

aidlc_queueread

Ready, blocked, and parked work units.

aidlc_reportwrite · policy checked

Submit results and supported gate decisions only through existing report validation and configured human/AI rules. Human allowlists constrain caller-supplied names but do not authenticate them; host confirmation is not guaranteed.

Dashboard signal

CLI still stands alone

Setup, administration, shell use, and fallback do not depend on an MCP host.

No second workflow engine

State transitions and policy belong in shared operations, not in a parallel MCP implementation.

Local by default

MCP uses stdio and opens no listener. The separate monitor serves read-only HTTP on loopback; the project owns its state.

Audit is not telemetry

The existing append-only audit log records workflow audit events. Proposed bounded, best-effort telemetry is separate and never authorizes writes.

Loopback still needs defenses

Loopback is not process isolation. Review Host/Origin, CORS, DNS rebinding, local access, and whether a per-run read token is needed.

Defaults remain open

Telemetry enablement and retention need a decision. Metadata spans are operational signals, not OpenTelemetry export or proof of an audited gate decision.
