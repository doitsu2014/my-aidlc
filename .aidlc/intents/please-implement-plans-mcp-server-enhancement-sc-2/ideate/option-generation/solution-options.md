## 1. Common to all options

Everything in this section is identical whichever option is chosen. It is described once and is not repeated in the option sections or in the trade-off matrix, except where an option changes it.

### 1.1 Telemetry semantics shared by every option

- **Location and file layout (Q6, AC-008, AC-012).** `.aidlc/telemetry/` (plan:185, design:164, impl plan s3.4). One file per MCP process: `mcp-<UTC yyyymmddThhmmssZ>-<pid>-<session8>-<part 3 digits>.jsonl`, matched by one strict pattern that the writer and the monitor reader share. Directory created 0o700 on Unix (DirBuilderExt), files `create_new` + 0o600 (pattern from `rust-cli/audit.rs:172-195`, Observed by research). `create_new` refuses an existing path or symlink, so a name collision retries with the next suffix (AC-012 "Name collision", R8). Windows relies on inherited ACLs, documented (Assumption, R7). An Option that uses another location is in section 4.
- **Never creates `.aidlc` (R1, ASM5).** The sink writes only when `.aidlc` already exists, passes `assert_safe_state_dir`, and `.aidlc/telemetry` is not a symlink or non-directory (lstat). If `.aidlc` is absent, events are dropped silently with no stderr (keeps `tests/mcp_stdio.rs:155-163` and `:548-549` true, Observed by research). A real write failure gives one fixed stderr line with no path (AC-008 symlink scenario, AC-010).
- **Lazy creation.** Nothing is created until the first event of a `tools/call` or protocol error. An MCP process that only sees an empty stdin writes nothing (keeps `ts005_empty_stdin_exits_zero_and_writes_nothing` and the installer smoke checks valid; release thread, Assumption until tested).
- **Git ignore (R2, AC-008).** Add exactly one `/telemetry/` line to IGNORE_BLOCK (`rust-cli/knowledge.rs:22`), keeping marker `v1` (CON3 c), and write a self-ignore `.aidlc/telemetry/.gitignore` containing `*` when the directory is created (ENGINE_GITIGNORE pattern, `rust-cli/orchestrate.rs:96-98`). The self-ignore covers projects that never run `next` (Observed: `ensure_ignore_file` runs only from `finish_directive`).
- **Retention (Q6, AC-009).** 5 MiB per file, 7 days by mtime, 50 MiB total (plan proposal; Estimate, not measured beyond the spike). At the per-file cap open the next part file (do not stop; this settles AC-009 scenario 2 as "new file"). Prune at writer start and at each rollover only: age-expired first, then oldest-first until under the total; only pattern-matching regular files (symlink_metadata), never this process's current file, every delete error ignored. Known ceiling (Estimate): between prunes the total can exceed 50 MiB by up to one open file (5 MiB) per concurrent process. Windows delete of another live process's file: Assumption that std opens with FILE_SHARE_DELETE so the delete becomes delete-pending; errors are ignored either way; verify on windows-latest CI (R7).
- **Opt-out (Q1, Q20, AC-001).** `dtech-aidlc-mcp --telemetry off|on` (plan:119, :340). Default `on`. `parse_args` becomes an order-independent loop returning `{project, telemetry}`, refusing duplicates and a missing value; the unit test `parse_args_accepts_only_project` and the `tests/mcp_stdio.rs:196` refusal loop change (test-source edits listed in open-questions.md, not golden re-blesses). No env var (YAGNI; the decision says "flag"). When off, the sink is never constructed: no file is created or changed (AC-001 scenario 1).
- **Event vocabulary v1 (Q8, AC-003, AC-004..AC-007).** Produced: `mcp.request.started`, `mcp.tool.completed`, `mcp.protocol.error`, `operation.started`, `operation.completed`, `workflow.stage_selected`, `workflow.stage_reported`, `workflow.gate_decided`. Dropped from the v1 enumeration: `workflow.unit_parked`, `workflow.unit_revisited`, intent pause/resume/abandon (not reachable over MCP, ADR-009; the CLI writes none, OD1). Listing names that are never produced would fail AC-003, so they are removed from the schema, and the dashboard coverage line says they are not observed (AC-006 "Coverage gap shown", AC-017). `component` takes `mcp` or `application`; `caller` is always `mcp` (CON18). The plan's `cli` enum value is not produced in v1.
- **Allowlist (AC-002, OD9, CON8, R5).** Exactly the AC-002 field set, built with an explicit field-by-field constructor, never a generic Value. `name` is the shipped tool name (`status`, `queue`, `next`, `report`) only when the tool is known; an unknown tool's raw name is never stored. Ids pass the existing `tools.rs` validators and 64-character caps or are dropped. No `detail`, `approved_by`, message text, path or raw frame.
- **Outcome and error mapping (Q9, AC-004, AC-005, R6).** `mcp.tool.completed`: directive/complete -> ok; blocked/busy -> blocked (ADR-007); status/queue Ok -> ok; `isError` -> error with `errorCode` = the existing four codes (invalid_arguments, approver_required, state_conflict, operation_failed; `tools.rs:203`); unknown tool -> error/`unknown_tool`; caught panic -> error/`internal_error`. `mcp.protocol.error` uses a fixed table keyed by the reply code only: -32700 parse_error; -32600 invalid_request; -32601 method_not_found; -32602 invalid_params; -32022 unsupported_protocol_version; -32603 internal_error. An oversized frame and a malformed envelope both reply -32600 (Observed `protocol.rs:203` and `:256`), so both map to `invalid_request`; a separate `line_too_long` value would need the hook to carry a reason tag (1.1 "Protocol-error hook"), which no option proposes in v1. No typed-error work (ADR-008 stands). An unknown tool yields one tool span and one invalid_params protocol error; these are separate dashboard populations (design s7.4).
- **Calls rejected before the tool host (AC-004 interpretation).** `serve` replies -32602 to a `tools/call` with no string `name` or with non-object `arguments` before `host.call` runs (Observed `protocol.rs:107-115`). Every option emits tool spans from the adapter (A, C, D via `traced_call`; B keeps tool spans in the adapter too), so such a call, including a known tool with array arguments, yields only one `mcp.protocol.error` (invalid_params) and no start/completion pair. This reads AC-004 "each tool call that reaches the server" as "each call that reaches the tool host", and its "Invalid arguments" scenario as covered by the protocol-error event for envelope-level argument errors and by the tool span (errorCode invalid_arguments) for tool-level ones. Rated Met* in section 3 for every option; direction-selection confirms the reading or moves span emission into `serve`.
- **Ids (OD2).** `sessionId` per process: 16-byte hex from RandomState/SipHash (or sha2) over (start nanos, pid, a RandomState u64). `eventId`, `traceId`, `spanId` = `<sessionId>-<AtomicU64 counter>` (unique within a process by construction; design s6.3 says ids are dedup keys, not credentials). Uniqueness across processes rests on `sessionId` (128 bits from RandomState/SipHash over start nanos, pid and a RandomState u64; no cross-process collision test exists, Assumption). Note: the telemetry spike's "400,000 ids unique across 8 threads, length 32" (Observed, re-run in review) measured a different generator (`telemetry-storage/spike.rs:17-29`, a fresh RandomState SipHash per id, two halves), not the counter scheme, and says nothing about cross-process `sessionId` collisions. These ids are never used as a monitor token.
- **Workflow events after durability (AC-007).** `stage_selected` after `application::next` returns a Directive (finish_directive has run); `stage_reported` after `application::report` returns Ok; `gate_decided` after report Ok when the call carried `approval` (state and audit already persisted). A failed or conflicting report emits only an error operation event.
- **Stdout and lock (AC-028, CON11, CON12, R4).** Telemetry never writes stdout and never takes `with_state_lock`.
- **Protocol-error hook.** ToolHost (`protocol.rs:13-17`) gains one `on_error: fn(&C, i64)` field called by `serve` whenever a reply carries an error; 2 construction sites (`mcp/mod.rs:68`, the protocol test HOST). Keeps the SDK-swap seam (R6). It carries the code only, so the mapping above cannot separate reasons that share a code (oversized frame vs malformed envelope, both -32600). Widening it to `fn(&C, i64, &'static str)` is a small additive change if the AI design review wants that split.
- **Monitor settings shown (Q20, AC-001, AC-017).** No trusted "configured off" input can reach the monitor: the opt-out lives in the MCP host's launch args and the CLI writes no settings (OD1); writing an "off" marker would break AC-001 scenario 1. Every option therefore shows "Setting: unknown, configured in your MCP host launch arguments" and never renders the "off (trusted input only)" state in v1. The AI design review must record this so AC-017 is not read as broken (Open question for the reviewer). Two readings exist: (1) strict, "every state" includes "off", so never showing it is a gap (section 3 rates AC-017 Partial for A-C on this reading); (2) the "off" state is defined as conditional on trusted input, and AC-001 scenario 2 requires "unknown" when no trusted input exists, so never showing "off" in v1 is compliant. The release gate should apply reading (2) unless direction-selection rules otherwise, so this item is not counted as a failure. Liveness is always "unknown" (no heartbeat; plan s3.5 excludes process events).

### 1.2 Monitor command surface shared by options A, B, C and D

- `dtech-aidlc monitor`, zero command flags, global `--project` only, 0 positional args (monitor thread, Observed edits): `rust-cli/args.rs` COMMANDS, command_flags, command_max_args and the table test; one `help.txt` line; one `completion.zsh` entry; one dispatch arm in `main.rs` after `assert_safe_state_dir`, so an unsafe `.aidlc` exits 1 with the existing message. - UI assets embedded with `include_str!` from a new monitor module (main.rs:48/93 pattern), not in `embedded::ASSETS` (which `scope.rs` reads as methodology). No build.rs change. Read-only: never opens a file for writing, never calls `create_dir`, `application::open` or `with_state_lock`, never reads state.json, audit.jsonl or artifacts; lists only `.aidlc/telemetry`, accepts only pattern-matching regular files (AC-014, AC-016, CON12).
- Read model shared by the server options (A, B, C): newest first, tie-break timestamp then eventId; allowlisted fields re-serialised, unknown fields dropped, malformed lines counted as skipped, a trailing line without newline shown as "partial tail" (AC-003 scenario 2, AC-017). Range presets 900, 3600, 86400, 604800 s ("all retained" = 7-day retention); above 604800 s -> `range_too_large` (gives AC-016 "Range above the maximum" a testable value; Estimate). Read caps 512 files, 64 MiB, 250k events -> `query_limit_reached` (Estimate). Per-file parse cache keyed by (len, mtime).
- Missing or expired files (proposal for direction-selection, Open question; applies to A-D). Pruning runs only when an MCP writer starts or rolls over, so with no MCP process running, files older than 7 days stay on disk. Because the maximum range is 604800 s, their events fall outside every range and are not shown. The monitor counts such pattern-matching files and shows "N files older than retention not shown (removed at the next MCP start)" in the coverage line; it never deletes them (read-only, AC-014). If `.aidlc` or `.aidlc/telemetry` is absent, the monitor starts and shows the empty state "no telemetry observed" (AC-017). This is a normal state for a project that never ran the MCP server, and `assert_safe_state_dir` already passes when `.aidlc` is absent (Observed `rust-cli/audit.rs:101-116`). A nonzero exit (AC-013 "Cannot start") is reserved for an unsafe location (a symlink or non-directory `.aidlc` or `.aidlc/telemetry`), an unreadable directory, or a bind failure. This reads AC-013's "telemetry location is unavailable" as "unsafe or unreadable", not "absent".
- Metrics (AC-018, Q14): tool calls = distinct `mcp.tool.completed` eventIds; errors and blocked use that population with numerator/denominator; a start without completion is "incomplete"; p50/p95 only at n >= 20 with n shown, else "insufficient samples" (Estimate threshold); operation counts are a separate population.
- Dashboard states (AC-017, Q14): empty ("no telemetry observed", never "process absent"); recent; partial/corrupt with skipped count; quiet (no event in 15 min, Estimate); stale (refresh failed or last success older than 3 intervals; 5 s polling, backoff to 60 s, paused while hidden; Estimates); store unavailable; liveness unknown; limit reached; connection lost / shutting down (client-detected, R13); setting unknown (1.1).
- Accessibility (AC-021): native controls, landmarks, `<table>` with caption, row button opens an `<aside>` detail with focus management, one polite status region, text + shape for outcomes, `:focus-visible`, reduced-motion guard, no horizontal scroll at 320 px (the stricter of quality-requirements 320 px and AC-021 360 px), data inserted only via `textContent`. Colour tokens and light/dark media query reused from the HTML; system font stacks.

## 2. Options

The options differ on three axes: how telemetry is written and where the operation hook sits; how the monitor process is shaped; and how the loopback HTTP server queries and authorises. Option D replaces the server with a static snapshot.

**The axes are independent.** Options A-D are four named bundles, not the only valid combinations. Every element below combines with every other except where the table says otherwise. Direction-selection may pick per row.

| Axis | Choices | Used by | Constraint or effect when mixed |
|---|---|---|---|
| T1 write path | background bounded writer / synchronous append with disable latch | A, C, D / B | Synchronous: no silent drops (AC-004/AC-018 drop condition disappears), about 40 fewer lines, no thread or EOF flush wait. But AC-028 scenario 4 becomes Partial unless the owner sets the stall bound to "OS write time" (R3). Background: AC-028 Met, but drops when the queue fills (AC-004/AC-018 Met*). |
| T2 operation hook | MCP adapter `traced_call` / facade in `application.rs` | A, C, D / B | Either works with either T1 choice. Facade puts per-process sink state into `Project`, which fires ADR-006 "Reopen if" (decision-record.md:142). |
| T3 test isolation | `--telemetry off` in test spawns / snapshot helper skips `.aidlc/telemetry` | A, C, D / B | Either works with either T1 or T2 choice. The snapshot skip is optional in every bundle, including B: the plan does not require it, and only the snapshot skip needs owner written approval (Q24). |
| M1 monitor process | in-process foreground / supervisor + env-var child / static snapshot to stdout | A, C / B / D | The snapshot removes the M2/M3 rows and fails AC-013. |
| M2 query and assets | server-side query + cursor, two embedded files, `script-src 'self'` / bounded bundle, browser-side filter and paging | A, B / C | The bundle works with A's two-file asset layout, so C does not need an inline script (Option C). |
| M3 token | OS-RNG token in URL fragment / OS-RNG token typed into page / none | A / B / C | Any token choice works with any M1 server choice. "None" needs the AC-030 review to accept single-user hosts. |

Example of a combination no bundle shows: T1 synchronous + T2 adapter + T3 test flag with C's (or A's) monitor. This is the cheapest live combination (Estimate: C's effort less about 0.25 day for the writer thread). It has no owner-gated test change and no ADR-006 reopen, and its only cost is the AC-028 stall bound. B without its Q24 element (B with T3 = test flag) is fully compliant with the owner decisions; its "Conditional" status in the matrix comes only from the optional snapshot skip.

### Option A - Background writer, in-process monitor, server-side query, OS-RNG token in the URL fragment

**Summary.**
- Telemetry write path: background writer thread fed by a bounded `std::sync::mpsc::sync_channel` (256-1024 lines, Estimate) via `try_send`. Full queue -> event dropped and counted in memory only (the count never reaches the file or the dashboard). Observed in a review re-run (`spike2/review/tspike`): with the writer stalled at 50 ms per event, 257 events were sent and 743 dropped. This makes AC-004 and AC-018 Met* (section 3): met only while the queue does not fill, unless drops are counted and disclosed. Two choices for direction-selection: (a) write the pending drop count into the next event that is written (needs one allowlisted field, an AC-002 change Analyze would own) so the dashboard can show it; or (b) state in the AC-020 disclosure that events may be dropped when the disk stalls, and show "dropped events: not recorded" in the coverage line. Disconnected (writer failed or panicked) -> telemetry disabled for the process with one fixed stderr line. Producer stamps timestamp and duration itself. At EOF: drop the sender and wait up to 500 ms (Estimate) for the writer, then exit.
- Hook (Q22): a `traced_call` wrapper in `rust-cli/mcp/tools.rs` becomes `ToolHost.call`. It emits the tool span, the operation pair (component `application`, caller `mcp`) around `application::open` plus the operation, and the workflow events; its own `catch_unwind`/`resume_unwind` keeps protocol.rs:231's -32603 behaviour. `application.rs` and the CLI path are untouched.
- Tests (Q24): `run_mcp_env` and the two direct spawns (`tests/mcp_stdio.rs:240`, `tests/mcp_parity.rs:395`) pass `--telemetry off` (about 3 test-source lines). Each existing snapshot then also proves "off writes nothing" (AC-001). A new telemetry test file runs with telemetry on.
- Monitor (Q19): in-process foreground `dtech-aidlc monitor`. Binds 127.0.0.1:0, prints `monitor: http://127.0.0.1:<port>/#token=<32 hex>` on stderr, Ctrl+C ends the process with default signal handling (spike Observed, `http/shutdown-results.txt` case A, interactive job control: exit 130, no process left). Caveat (same file, case B, and `http/results.txt` "after SIGINT: exit=143"): a background job of a non-interactive script inherits SIGINT as SIG_IGN, survives SIGINT, and needs SIGTERM (exit 143). AC-013 tests must therefore stop the monitor with SIGTERM (Unix) or kill the child directly rather than send SIGINT from a script. Wrappers that launch it in the background (CI steps, launch scripts) must forward SIGTERM. Installing a SIGINT handler would need FFI or a crate, so v1 documents the behaviour instead.
- HTTP: std `TcpListener`, thread per connection, hard cap 16 (503 `busy`), total 5 s head deadline recomputed before each read (spike Observed: slowloris gets 408 at 5 s), 8 KiB head cap (431), GET only (405 + `Allow: GET`), exact Host and Origin checks, no `Access-Control-*`, no request body, `Connection: close`, fixed security headers. Two embedded files (`index.html`, `app.js`) so the CSP can be `script-src 'self'` without `unsafe-inline`. Server-side filtering and paging on one route `GET /api/events` with an opaque cursor bound to the normalised query and frozen `to` (`cursor_stale` on mismatch). Error codes follow design s7.7: `invalid_filter`, `range_too_large`, `cursor_stale`, `store_unavailable`, `query_limit_reached`, plus method/host/origin/token codes.
- Token (Q7): 128 bits from the OS RNG: `/dev/urandom` on Unix (no unsafe); `BCryptGenRandom` or `ProcessPrng` via `extern "system"` on Windows (about 8 lines unsafe, precedent `rust-cli/dependencies.rs:339-361`; not built yet). Not RandomState: std gives it no cryptographic guarantee (ASM2). Not `std::random` either: negative result Observed in the review, it is unstable on rustc 1.100 (error E0658), so the OS-RNG read plus Win32 FFI is the only std-only CSPRNG path. Delivered in the URL fragment (never sent in the request line or Referer), read by the page, removed with `history.replaceState`, kept in a JS variable only (not sessionStorage), sent as `Authorization: Bearer` on `/api/*`, compared in constant time. The custom header forces a preflight that gets 405 with no CORS headers. A reload shows "token missing: reopen the address printed in the terminal" (fits AC-019 reload).

**What it leaves out.** Server-pushed "shutting down" (shown as client "connection lost", R13); dropped-event counts on the dashboard (counted in memory only, no schema field; this is why AC-004, AC-018 and AC-020 are Met* for A); chart click-to-filter by time bucket (only summary counts link to filters; simplification of plan s3.6 for the AI design review); an env-var opt-out; any "configured off" display (1.1).

**Risks.** R3 (write failure or panic) mitigated by the thread + channel, R4 (stdout) by construction, R9 (hand-rolled parser) and R10 (rebinding) by the spike-tested checks, R11 by exact routes and pattern-only file reads, R12 by cap and deadline (residual: one local client can hold 16 slots for 5 s windows, Assumption acceptable locally), R13 by in-process design, R22 by n >= 20 and "unknown" liveness. Residual: token visible in terminal scrollback and browser history/autocomplete (document in AC-030 review); Windows CSPRNG FFI and firewall prompt (ASM6) not run; events silently dropped when the queue is full.

**Effort (Estimate).** Telemetry writer + hooks + tests about 700-800 lines, 1.5-2 work units (research). Monitor server + reader + UI + tests about 3-4 dev-days (research). Option-specific total about 5-7 dev-days (telemetry about 2-3 dev-days, my conversion of the work-unit figure), plus common 4-5.

**Reversibility.** High for internals: the writer can become synchronous, the token bootstrap can change, a supervisor can be added later without changing the URL or API. Medium for the on-disk event format and directory once released (schemaVersion lets readers tolerate change, AC-003).

**Plan contradictions named.**
- Plan:305, :500 and design s7.7 (:345) require a foreground supervisor that self-launches a hidden child via `current_exe`; A runs in-process (ASM3). Needs an ADR superseding that plan text.
- Plan s3.6 (:278, :309) and design s7.4 (:312) say no token in URL query/hash; A puts it in the fragment. Needs an ADR amending the rule (the fragment is never transmitted and is stripped on load).
- Design s6.3 names the "shared application façade around each public operation" as the operation-event producer, and ADR-006's consequence note says the facade is the intent-2 hook; A emits operation events from the MCP adapter (Q22, CON4). Needs an ADR note; ADR-006's "reopen if" (per-process state) is not triggered because no per-process state enters the facade.
- Plan s3.7 "config override" and design s8 "Monitor: optional bounded time window": no config key, zero monitor flags.
- Plan/design schema enum `cli` component and park/revisit events are not produced (CON18, Q8).
- Plan:119 lists `--help`/`--version` as MCP process arguments. Intent-1 already decided against them ("no `--version` or `--help`", `interfaces-and-contracts.md:151`), and the shipped binary refuses both. No option adds them; this deviation is shared by A-D.

### Option B - Plan-literal: synchronous sink at the facade, supervisor with hidden child, token typed into the page

**Summary.**
- Telemetry write path: synchronous inline append on the caller thread (file opened once, one `write_all` per line; spike Observed 1.75 us per event on macOS APFS), wrapped in `catch_unwind`, with a latch that disables the sink after the first io error or panic.
- Hook (Q22): inside `rust-cli/application.rs`, as design s6.3 and ADR-006's consequence note describe. `Project` gains an optional sink; the CLI passes `None` (no-op for `Caller::Cli`, CON4). Tool spans and protocol errors stay in the MCP adapter (`ToolHost.on_error`).
- Tests (Q24, optional element: B works unchanged with A's `--telemetry off` test flag, and then needs no owner approval and keeps AC-001 evidence in existing snapshots): the shared snapshot helper (`tests/fixtures/mcp/common.rs:244-266`) skips `.aidlc/telemetry` as it skips `.aidlc/engine` today, so every MCP test runs with telemetry ON. This changes what 24 snapshot assertions compare and **requires owner written approval** (gate-recommendation follow-up; Q2/Q4). AC-001 "off writes nothing" needs its own test.
- Monitor (Q19): `dtech-aidlc monitor` is a foreground supervisor that spawns `current_exe` in a private child mode and waits. The private mode is an environment variable, not a flag, because a registered hidden flag breaks the `tests/repo_content.rs:1353-1372` help invariant. The child exits on stdin EOF (spike Observed: exits 0 within 1 s when the parent is SIGKILLed), the only std-portable dead-parent signal.
- HTTP: same std server and server-side query as A.
- Token (Q7): same OS-RNG source as A, but never in a URL. The child prints the URL and, on a separate stderr line, the token; the page shows a token form; the user pastes it; the page keeps it in a JS variable and sends it as Bearer. Matches plan:278/309 and design:312 literally.

**What it leaves out.** A host reply that never waits on disk (synchronous write; see risks); exact AC-001 evidence from existing snapshots (only with the optional snapshot skip); server-pushed "shutting down"; the same items as A otherwise.

**Risks.** R3 is only partly mitigated: std files have no write timeout, so a hung disk, network share or Windows AV scan blocks the tool reply, failing AC-028 "write stalls" unless the owner accepts "whatever the OS write takes" as the bound (Open question, owner). With the optional snapshot skip, R1 is resolved only by the Q24 owner approval; with the test flag, as in A. R13 grows: a SIGKILLed supervisor leaves the child until stdin EOF propagates; supervisor/child cleanup tests on three OSes. R16: the env-var private mode is an undocumented entry point. R9/R10/R11/R12 as in A. Higher friction token flow: the first load needs a paste. A reload loses the token in both A and B (A: reopen the printed address; B: paste again), so reload is not a difference between them.

**Effort (Estimate).** Telemetry about 600-700 lines (1.5 work units, research) plus facade plumbing about 0.5 day. Monitor as A plus 1-1.5 dev-days for supervisor, child mode and cleanup tests (monitor thread) plus about 0.25 day for the token form. Option-specific total about 6.5-8 dev-days, plus common 4-5.

**Reversibility.** Medium. Moving the hook out of `application.rs` later is a refactor of shared code; dropping the supervisor later is easy; the Q24 snapshot change is test-only but, once made, existing snapshots stop guarding "off writes nothing".

**Plan contradictions named.** Few: the private child mode is an env var, not the "private monitor-child flag" of plan s8 item 2; the synchronous design meets the plan but not AC-028 scenario 4 as written. Same enum/park-revisit/config-override and plan:119 `--help`/`--version` contradictions as A.

**ADR touched.** B follows ADR-006's consequence note (the facade is the intent-2 hook), but it also fires ADR-006's "Reopen if ... intent 2 telemetry needs per-process state" (decision-record.md:142). `Project` gains an optional sink whose file is opened once per process, which is per-process state inside the facade. B must therefore record ADR-006 as reopened and amended (or superseded) by a new ADR. It is not ADR-clean.

**Owner-decision status.** The Q24 snapshot skip is an optional element of B, not something the plan or the facade hook needs: a synchronous facade hook works with the `--telemetry off` test flag. With the test flag, B is compliant. With the snapshot skip, B is compliant only if the owner approves it in writing.

### Option C - Lean: background writer, in-process monitor, no token, bounded bundle filtered in the browser

**Summary.**
- Telemetry: identical to A (background writer, adapter hook, tests pass `--telemetry off`).
- Monitor: in-process foreground as A.
- HTTP: same hardened std server. Assets: reuse A's two embedded files (`index.html`, `app.js`) with `script-src 'self'`, which needs no extra code. The research variant (one `index.html` with an inline script and CSP `script-src 'sha256-<base64>'`) is extra work for no gain. The digest comes from the existing `sha2` dependency, but the CSP source needs base64 of it, and std has no base64, so that variant also needs a small hand-rolled encoder (about 20 lines, Estimate). One data route `GET /api/events?range=<preset>` returns all allowlisted events in the range up to a hard cap (for example 20,000 events or 8 MiB, Estimate) with `limitReached`; filtering, paging and the cursor run in the browser.
- No token: protection is loopback bind, exact Host/Origin, no CORS, GET only. The address printed is `http://127.0.0.1:<port>/`.

**What it leaves out.** Protection against another OS user on a shared machine, who can open a loopback connection with any Host header and read telemetry that 0o600 files deny them (Assumption, threat analysis). A server-bound cursor: AC-019 "stale cursor" is met only as a client-side message when filters change. Full "all retained" views: large stores hit `limitReached` more often than in A. Server-side bounds per page.

**Risks.** R10 residual (shared multi-user hosts) must be accepted in the AC-030 threat review (Q7); R12 (response size) bounded by the cap but responses are larger; R9/R11 as A. Lower risk of RNG/FFI bugs (no token, no Windows FFI).

**Effort (Estimate).** Telemetry as A. Monitor about 2-2.5 dev-days (A minus about 0.5-1 day for server-side query/cursor and about 0.25 day for the token). Option-specific total about 4-5.5 dev-days (telemetry 2-3 + monitor 2-2.5), plus common 4-5.

**Reversibility.** High: adding a token later is additive (a new printed URL form); moving filtering server-side later changes only the monitor's private API (no external consumer).

**Plan contradictions named.** Same as A for the supervisor, the adapter hook and plan:119 `--help`/`--version`. Additionally, two lines require a server query cursor: plan:288 ("The API provides ... cursor pagination") and design:348 ("Query interface accepts ... opaque cursor"). C uses a client-side cursor instead. Plan:277 and design:311 allow "cursor pagination or a bounded virtualized window", and C's bounded bundle with client paging satisfies them, so C contradicts only plan:288 and design:348. Also plan s8 item 6 "select a secure per-run token/bootstrap strategy" (C selects none after review). C does not contradict the no-token-in-URL rule.

### Option D - Static snapshot: telemetry as A, `dtech-aidlc monitor` prints a self-contained HTML report

**Summary.** Telemetry identical to A. `dtech-aidlc monitor` reads `.aidlc/telemetry`, applies the same parser, allowlist and caps, and writes one self-contained HTML file (embedded JSON, inline script, no remote asset) to stdout for the user to redirect. No socket, no token, no HTTP code. Filtering and detail run in the page. Nothing is written under `.aidlc`.

**What it leaves out.** A foreground server and printed address (AC-013), refresh, stale, connection-lost and shutting-down states (AC-017), server cursor (AC-019 "stale cursor" only client-side), the loopback HTTP surface entirely (AC-014/AC-015 become vacuous rather than met). It answers the plan's three questions only for a moment in time.

**Risks.** Lowest security surface (removes R9, R10, R12, R13). New risk: the redirected HTML is an at-rest copy of telemetry outside `.aidlc/telemetry/`, outside the managed ignore line and the retention policy (privacy, R5); the user may commit or share it. AC-013/AC-017 failing means the release gate fails unless the owner amends those ACs (Analyze owns them).

**Effort (Estimate).** Telemetry as A. Snapshot about 1.5-2 dev-days (monitor thread). Option-specific total about 3.5-5 dev-days, plus common 4-5.

**Reversibility.** High technically (a server can be added later and the snapshot kept as an export), but shipping D means releasing 1.3.0 with AC-013 and parts of AC-017/AC-019 unmet.

**Plan contradictions named.** Plan s3.6 and design s7.7 (separate monitor process, loopback HTTP, refresh, API with cursor), plan Phase 4 exit ("live local events"), the HTML diagram "Monitor process · 127.0.0.1 HTTP"; as A for the adapter hook and plan:119 `--help`/`--version`. Feasible under the owner decisions (none forbids it), but not viable against AC-013 without an AC change.

## 5. Open questions for direction-selection (technical; none needs a new owner decision unless noted)

- Q7: fragment (A) vs typed token (B) vs none (C); confirm OS RNG source; constant-time compare. The fragment choice amends plan:278/309 and design:312.
- Q14 values to confirm (all Estimates): writer queue 256-1024; EOF flush wait 500 ms; AC-028 stall bound = "never waits on disk" (A/C/D) or "OS write time" (B, owner); max range 604800 s; quiet 15 min; stale > 3 intervals at 5 s; page 50 (max 200); read caps 512 files / 64 MiB / 250k events; connection cap 16; timeouts 5 s; percentile n >= 20.
- Q19: in-process (A, C) vs supervisor (B); record an ADR either way.
- Q22: adapter wrapper (A, C, D) vs facade branch (B; reopens ADR-006 because the sink is per-process state in `Project`).
- Q24: test flag (A, C, D, and B if chosen) vs snapshot skip (optional in B; owner written approval required). Independent of Q22 and of the write path (section 2 axis table).
- Research threads disagree (Observed): the HTTP spike accepts `Host: localhost:<port>` and answers 421 for a foreign or missing Host; the monitor spike rejects `localhost` and answers 403. The HTTP spike stores the token in sessionStorage; the monitor thread keeps it in a JS variable (design s7.4 forbids persistent browser storage). Pick one set of codes aligned with design s7.7 names.
- `workflow.gate_decided` decision value: AC-002 has no field for approved/rejected; research suggests `name: approved|rejected` (stretches `name`). Schema decision needed.
- ADR-002 says the MCP binary takes `--help` and `--version`, but the shipped binary refuses both (Observed `rust-cli/mcp/mod.rs:12-24`, `tests/mcp_stdio.rs:196-206`). This is not open: intent-1 Develop already decided it, "no `--version` or `--help`" (Observed `.aidlc/intents/please-implement-plans-mcp-server-enhancement-sc/develop/implementation-design/interfaces-and-contracts.md:151`). Every option follows that contract (1.3 (e) asserts exit 1 for both; the installer smoke check uses initialize + tools/list) and records plan:119 as superseded plan text. The only remaining step is a consistency note against ADR-002 in the new ADR set.
- Monitor edge (proposal in 1.2, confirm): expired-but-present files are counted and not shown; absent `.aidlc` or `.aidlc/telemetry` gives the empty state, not a nonzero exit.
