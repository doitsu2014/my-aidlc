## ADR-001 Hand-rolled JSON-RPC over stdio instead of an MCP SDK

- **Context.** The plans require an SDK unless an ADR documents a blocker: design s4.2 ("Do not implement JSON-RPC framing by hand unless an ADR documents the SDK blocker and a conformance plan") and plan Phase 0 step 3 (observability plan line 354). Q3 (owner, 2026-11-27) allows at most one reviewed SDK tree for the MCP binary only, and explicitly allows hand-rolled JSON-RPC when it is recorded in an ADR. Packaging spikes showed that an SDK in the root package or in a workspace member breaks the CLI's clean-cache offline `--locked` install (Observed, packaging A1, B1), while an SDK in a nested standalone package does not break the CLI (Observed, B2-1/B2-2) but adds about 62 lock entries plus tokio and has its own offline gap.
- **Decision.** Implement the MCP protocol by hand: JSON-RPC 2.0, one message per line on stdin and stdout, parsed and serialised only with `serde_json` (no hand-written JSON parser), synchronous `std::io`, one request at a time, tools only. **Blocker as recorded:** the owner chose Option A over Option B, with zero new crates, an ADR, and offline `--locked` install working for both binaries from one lockfile (User-provided, 2026-11-27). Supporting evidence, not an owner statement: trade-off-matrix decision axis 3 (own the protocol code versus track an upstream SDK) and the rmcp release history, which shows three majors in 2026 and 3.10-3.12 within 14 days (Observed, 2026-11-27). This is Q3's ADR allowance, applied as an owner choice. It is not a claim that no SDK could work: Option B shows an isolated SDK is technically feasible (solution-options.md Option A, "Plan conflicts").
  - **Conformance plan.** (1) Cargo integration tests spawn `env!("CARGO_BIN_EXE_dtech-aidlc-mcp")` with `std::process`, feed JSONL transcripts, assert stdout purity (every line parses as JSON-RPC 2.0), and compare responses by id as `serde_json::Value`, not as bytes. Result shapes are checked by exact `Value` equality against expected frames, because Q3 rules out a JSON Schema validator crate; implementation-design reviews each expected frame once against the saved schema.json files (2025-11-25 and 2026-07-28).
    - **Legacy-era cases:** a legacy handshake built from Claude Code 2.1.332's fallback frames (`initialize` 2025-11-25 with numeric id 0, `notifications/initialized`, `tools/list`, then `tools/call`), asserting legacy shapes with no `resultType`, `ttlMs`, `cacheScope` or `_meta`; version negotiation (2025-06-18 echoed; 2024-11-05 and `1900-01-01` answered with 2025-11-25; a missing version gets -32602); `ping` without the modern key gets `{}` before and after `initialize`; `tools/*` without the modern key before `initialize` gets -32602 (ADR-005 rule 4d).
    - **Modern-era cases (about 6, added by the owner's dual-era decision, ADR-004):** (M1) a replay of Claude Code 2.1.332's modern frames (`<spike>/decision-facilitator/cc-dual/frames.log`: `server/discover` with string id `"server-discover-probe-1"`, then `tools/list` with id 0), each compared to the exact expected DiscoverResult and ListToolsResult, and asserting no top-level `serverInfo`; (M2) a replay of TS client 2.4.0's modern probe process (discover, then EOF: exit 0 with exactly one result line; the EOF step is test design, since the observed client terminated its probe instead) and serving process (`tools/list`, a successful `tools/call`, an `isError` result, an unknown tool getting -32602; `ts-dual-auto.log`); (M3) version negotiation: `_meta` versions `"2025-11-25"` and `"9999-01-01"` get -32022 with `data: {supported:["2026-07-28"], requested}`, and a numeric or object version gets -32602; (M4) version present but `clientCapabilities` absent, null or an array gets -32602; (M5) era mixing in one process: legacy `initialize`, then a modern `tools/list` gets the modern shape, then a legacy `tools/list` gets the legacy shape; a modern `ping` gets -32601; `server/discover` without the modern key after `initialize` gets -32601; (M6) a shape sweep over every frame in M1-M5: every modern success result carries `resultType:"complete"` and `_meta["io.modelcontextprotocol/serverInfo"]`, no legacy result carries any modern field, no error response carries `resultType`, and the same `tools/call` returns equal `structuredContent` in both eras.
    - **Shared cases:** unknown tool and non-object arguments get -32602; an unknown argument field gets an `isError` result; parse error, batch array, null id, wrong `jsonrpc`, unknown method, notifications (with and without `_meta`) that get no reply, string and numeric ids; empty stdin gives zero stdout bytes and exit 0; an oversized line gets -32600 and the session continues; invalid UTF-8 gets -32700 and the session continues; one AC-004 session per era mixing valid calls, schema errors and domain errors.
    - (2) Manual release checks for AC-003 and Q1: `claude mcp list` shows Connected (Observed on 2026-11-27 with the dual-era spike on the modern path, and with its legacy-only mode on the fallback path), and a DeepSeek Harness launch-and-list (not yet run). Each check records which era the host negotiated. (3) Optional developer check: drive the server with `@modelcontextprotocol/client` in `auto` mode (pattern: `<spike>/decision-facilitator/tsclient/drive.mjs`). The official conformance suite is not used, because it is HTTP-only for servers (Observed, solution-options.md section 3A).
  - **Recorded spec deviation.** The 2025-11-25 tools page says servers "MUST ... Rate limit tool invocations" (Observed, https://modelcontextprotocol.io/specification/2025-11-25/server/tools, fetched 2026-11-27). No explicit limiter is added: the synchronous loop allows exactly one call in flight, the server serves one local host-launched client, and every write passes domain, gate and concurrency validation. Audit growth stays unbounded, as on the CLI today.
- **Status.** Owner-decided (User-provided, project owner, 2026-11-27: Option A "Lean hand-rolled", chosen explicitly over B, "ADR required"). The conformance plan and the rate-limit deviation are Recommended - pending gate approval.
- **Alternatives.** (B) rmcp 3.12.x isolated in a nested `mcp/` package with its own lockfile: feasible, CLI install unaffected, upstream conformance; rejected by the owner. (C) rmcp as an optional dependency of the root package: CLI clean-cache offline install fails (Observed A1/A2); infeasible under strict Q3. A later swap to an SDK remains possible (see Consequences).
- **Consequences.** Zero new crates and no dependency churn. We own protocol conformance and spec tracking for three revisions across two eras (the spec had five revisions in about 20 months, 2026-07-28 was breaking, and a twelve-month deprecation window applies; Observed, changelog). Assurance rests on transcripts plus manual host checks. Estimate: about 130-140 production lines for the dual-era protocol layer (about 95-100 for the legacy era plus 35-40 for the modern era, from the spikes), plus 250-450 test lines (about 6 more transcript cases than legacy-only). The plans' design s4.2, plan Phase 0 step 3 and Phase 2 step 2 ("through the selected SDK") are superseded by this owner decision under Q3 (see scope-boundary.md).
- **Reopen if.** A host requires a protocol feature that costs more by hand than an SDK would (for example a non-stdio transport, which is a non-goal today); the conformance burden grows past about one revision update per quarter; or the owner relaxes Q3 or accepts SDK churn. The swap is contained by the `(method, params) -> Result<Value, Value>` boundary (ADR-005).

## ADR-002 Packaging: second [[bin]] in the same package, zero new crates

- **Context.** AC-013 requires both executables to install, run and uninstall from outside the checkout, with the CLI working without MCP. Q3 requires that the CLI keeps only `serde_json` and `sha2`, that Cargo.lock is committed, and that `--locked` and offline install keep working. N2 asked whether the install scripts handle the MCP binary.
- **Decision.** Add `[[bin]] name = "dtech-aidlc-mcp"` to the existing `Cargo.toml` (source file per plan s3.2, for example `rust-cli/mcp_main.rs`; the exact file layout belongs to implementation-design). No `[features]`, no `required-features`, no new dependencies. `cargo install --path . --locked` installs both binaries, `cargo install ... --bin dtech-aidlc` still installs only the CLI, and `cargo uninstall dtech-aidlc` removes both (Observed, packaging C1 and C3). `tests/rust_cargo_install.rs` is extended to the MCP binary. The install scripts (`scripts/rust-install/install.sh`, `install.ps1`) stay CLI-only, and support for the second binary there is deferred to intent 2 (N2). The MCP binary's flags are `--project <path>` (optional, defaulting to the startup directory), `--help` and `--version`. There is no `--telemetry` flag in intent 1 (Q11).
- **Status.** Owner-decided (User-provided, 2026-11-27: second `[[bin]]` in the same package, zero new crates, offline `--locked` for both binaries; N2 scripts CLI-only). The flag set is Recommended - pending gate approval.
- **Alternatives.** A nested package (Option B layout): needs two install commands and two lockfiles. An optional dependency plus a feature (Option C): breaks offline install. A separate repository: unnecessary.
- **Consequences.** Cargo.lock is byte-identical. Each binary embeds the build.rs assets, so roughly double the on-disk size (A7, Estimate about 3.8 MB each, not measured). The offline install test must use a clean `CARGO_HOME` to detect regressions, because the warm cache on this machine masks them (Observed, solution-options fact 1). Add a Cargo.lock no-diff check.
- **Reopen if.** An SDK is adopted later (ADR-001 reopened), the owner wants script install support (intent 2), or binary size becomes a problem.

## ADR-003 MSRV pinned at 1.100

- **Context.** Q3 said "MSRV = current stable", and the open question was whether that means tracking each stable release or pinning once. rustc 1.100.0 is the observed toolchain, and the de-facto floor is at least 1.79 (`std::path::absolute`; constraint/dependency 1).
- **Decision.** Add `rust-version = "1.100"` to `[package]` now. Raise it only in a deliberate, changelogged change. The line does not change Cargo.lock (Assumption; implementation-design confirms with the offline install test).
- **Status.** Owner-decided (User-provided, 2026-11-27).
- **Alternatives.** Track stable automatically (rejected by the owner). Declare the de-facto floor of 1.79 (rejected: untested, and the owner chose 1.100).
- **Consequences.** Builds with toolchains older than 1.100 fail with a clear Cargo message. This is a user-visible constraint, and its CHANGELOG entry lands with the intent-2 release (ADR-018).
- **Reopen if.** A user or distributor needs an older toolchain, or a needed std feature requires a newer one.

## ADR-004 Protocol era: dual-era for v1

- **Context.** MCP now has two eras. Revision 2026-07-28 removes `initialize`, `initialized`, `ping` and `logging/setLevel`, and adds `server/discover`, per-request `_meta`, `resultType`, `ttlMs`/`cacheScope` and -32022 (Observed, 2026-07-28 changelog, 2026-11-27; re-checked 2026-11-27 against the saved schema: the 2026-07-28 `ClientRequest` union has no `ping` or `initialize`, and `ClientNotification` is only `notifications/cancelled`, `<spike>/decision-facilitator/web/schema_2026-07-28_schema.ts:3168-3181`). The spec compatibility matrix says a dual-era client with a legacy server "Works" (Observed, modelcontextprotocol.io/specification/2026-07-28/basic/versioning). The legacy `initialize` era is not on the deprecated-features registry, which lists only Roots, Sampling, Logging, DCR, includeContext and HTTP+SSE (Observed, .../2026-07-28/deprecated). Both target hosts are dual-era clients. The original Option A text was dual-era; variant A-legacy was listed as a real alternative (trade-off-matrix Summary bullet 4), and this stage first recommended it (see Status).
- **Decision.** Serve both eras from one process. The era is decided per request by the rules in ADR-005 rule 4; the session keeps only an `initialized` flag. `LEGACY = ["2025-11-25", "2025-06-18"]`, newest first; `MODERN = ["2026-07-28"]`.
  - **Legacy era (2025-11-25, 2025-06-18).**
    1. `initialize` with a string `params.protocolVersion` echoes that version if it is in LEGACY, and otherwise answers `"2025-11-25"`. This follows the 2025-11-25 lifecycle rule (Observed, modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle). A missing or non-string `protocolVersion` gets -32602. The result is exactly `{protocolVersion, capabilities:{tools:{}}, serverInfo:{name:"dtech-aidlc-mcp", version:CARGO_PKG_VERSION}}` (required: `protocolVersion`, `capabilities`, `serverInfo`; Observed, schema.json 2025-11-25), with no `listChanged`, `instructions` or logging capability. A repeated `initialize` is answered again by the same rule. Any `_meta` on `initialize` is ignored: `initialize` is always legacy.
    2. `notifications/initialized` is accepted and is not required before serving.
    3. `ping` exists only in the legacy era. A `ping` without the modern protocol-version key returns `{}` at any time, before or after `initialize`.
    4. Legacy results are exactly the 2025-11-25 shapes: `tools/list` is `{tools}` and `tools/call` is the ADR-008 result. No `resultType`, `ttlMs`, `cacheScope` or `_meta` is added (2025-11-25 `ListToolsResult` requires only `tools` and `CallToolResult` only `content`; Observed, schema.json 2025-11-25).
  - **Modern era (2026-07-28, stateless).** Field requirements re-verified on 2026-11-27 against `<spike>/decision-facilitator/web/schema_2026-07-28_schema.json` (`required` arrays) and `schema.ts`:
    5. **Per-request `_meta`.** `RequestMetaObject` requires `io.modelcontextprotocol/protocolVersion` (string) and `io.modelcontextprotocol/clientCapabilities` (object) (Observed, schema.json `required`; schema.ts:63-98: "Required." for both). A modern request whose version is not a string, or whose `clientCapabilities` is absent or not an object, gets -32602 (INVALID_PARAMS is for parameters that "are invalid or malformed", schema.ts:362; its Tools bullet, "a request that does not satisfy the `CallToolRequest` schema", schema.ts:366, is tool-specific; using it for a malformed `_meta` is this record's reading, not a spec sentence). A string version not in MODERN gets -32022 with `data: {supported: ["2026-07-28"], requested: <that string>}`; `code`, `data`, `data.supported` and `data.requested` are all required (Observed, schema.json `UnsupportedProtocolVersionError`; schema.ts:483-499). `clientInfo`, `logLevel`, `progressToken` and unknown `_meta` keys are ignored: the schema says servers SHOULD NOT change behaviour or make security decisions on `clientInfo` (schema.ts:78-89), and without a requested `logLevel` the server MUST NOT send `notifications/message` (schema.ts:100-104), which it never sends. Capabilities are never carried from an earlier request ("Servers MUST NOT infer capabilities from prior requests", schema.ts:92-97). The server requires no client capability and sends no server-to-client request, so -32021 is never returned.
    6. **`server/discover`** returns exactly `{supportedVersions:["2026-07-28"], capabilities:{tools:{}}, ttlMs:0, cacheScope:"private", resultType:"complete", _meta:{"io.modelcontextprotocol/serverInfo":{name:"dtech-aidlc-mcp", version:CARGO_PKG_VERSION}}}`. `DiscoverResult` requires `supportedVersions`, `capabilities`, `ttlMs`, `cacheScope` and `resultType`; its properties are only those plus `_meta` and `instructions` (Observed, schema.json). There is therefore **no top-level `serverInfo`** (the earlier `<spike>/mcp-protocol/handrolled` spike wrongly added one); server identity goes in `_meta["io.modelcontextprotocol/serverInfo"]` (`ResultMetaObject`, optional, SHOULD be included; schema.ts:142-158). No `instructions`. `supportedVersions` lists only modern versions, because legacy versions are negotiated through `initialize`, not through `_meta` (this reading of the spec is an Assumption; both hosts accepted the result, Observed).
    7. **`tools/list`** returns `{tools, ttlMs:0, cacheScope:"private", resultType:"complete", _meta:{serverInfo}}`. `ListToolsResult` requires `tools`, `ttlMs`, `cacheScope` and `resultType` (Observed, schema.json; it extends `PaginatedResult` and `CacheableResult`). No `nextCursor`: the four tools fit one page.
    8. **`tools/call`** returns the ADR-008 result plus `resultType:"complete"` and the `_meta` serverInfo. `CallToolResult` requires `content` and `resultType`; `structuredContent` is any value and `isError` optional (Observed, schema.json). Tool-execution failures (`isError: true`) are results, so they carry the same two fields. `inputResponses` and `requestState` (from `InputResponseRequestParams`, schema.ts:601-610) are ignored, and the server never returns `resultType: "input_required"`.
    9. `ping`, `initialize` and `logging/setLevel` do not exist in 2026-07-28: a modern `ping` gets -32601.
    10. **Cache hints.** `ttlMs: 0` ("SHOULD be considered immediately stale", schema.ts:1083-1095) and `cacheScope: "private"`, as spiked. The tool list changes only with the binary, so a positive TTL could come later; `0` makes no caching claim.
  - **Both eras.** Unknown methods sent with the key, or after `initialize`, return -32601 (keyless before `initialize` they get -32602, ADR-005 rule 4d): `resources/*`, `prompts/*`, `completion/complete`, `subscriptions/listen`, and in the legacy era `server/discover` without the modern key after `initialize`. Era stamping is done once, in the dispatcher, after the handler returns (ADR-005 rule 4f); the tool adapter and the facade never see the era. JSON-RPC error responses carry no `resultType` in either era.
- **Status.** **Owner-decided** (User-provided, project owner, 2026-11-27, AskUserQuestion in the conductor session): v1 is dual-era, serving the legacy `initialize` flow (2025-11-25, 2025-06-18) and the modern 2026-07-28 stateless flow. The per-request rules, the pre-initialize handling (ADR-005 rule 4), the cache hints and the error mapping are Recommended - pending gate approval.
  - **Superseded recommendation (kept for the record).** This stage first recommended legacy-only for v1 (`server/discover` answered -32601 so that dual-era hosts fall back), because it is a smaller conformance claim (two revisions, one era, no `resultType`/`ttlMs`/`cacheScope`/`_meta` stamping), needs about 6 fewer transcript cases, gives both hosts one code path, and avoids tracking modern revisions by hand. The owner was told that dual-era costs about 35-40 more lines, about 6 more transcript tests and 0.25-0.5 day, and that it keeps working if a host goes modern-only, and chose dual-era (User-provided, 2026-11-27). This record does not restate a reason beyond what the owner was shown; the modern-only resilience is the benefit on that list.
- **Alternatives.** (a) Legacy-only (the superseded recommendation): works today through both hosts' fallback (Observed: Claude Code `cc-legacy/frames.log`; TS client 2.4.0 `ts-legacy-auto.log`, `ts-legacy-auto2.log`) and is the smaller claim; not chosen by the owner, because it fails modern-only clients and needs a later upgrade. (b) Modern-only: rejected, because it fails AC-003's scenario ("host sends initialize then a tool-list request") and every legacy client. (c) Also accepting 2024-11-05 and 2025-03-26: rejected, because `structuredContent` exists only from 2025-06-18 and neither host offers older versions (Observed: both sent 2025-11-25 on the legacy path). Adding them later is a one-line change. (d) Listing legacy versions in `supportedVersions`: not chosen (see rule 6).
- **Evidence for host behaviour.** Dual-era (the spike's default mode, `<spike>/decision-facilitator/srv/src/main.rs`): Claude Code 2.1.332 sent `server/discover` with string id `"server-discover-probe-1"` and modern `_meta` (protocolVersion 2026-07-28, clientInfo, clientCapabilities with `roots` and `elicitation`), received the DiscoverResult, then sent `tools/list` with id 0 and the same `_meta` in the same process, and showed "Connected" on the modern path (Observed, `<spike>/decision-facilitator/cc-dual/frames.log`). TS client 2.4.0 in `auto` mode ran a probe process (discover, DiscoverResult, then terminated by the client: probe pid 86173 never logged the spike's `--- EOF exit` marker, so the server did not observe EOF) and then a serving process on 2026-07-28 in which `tools/list`, `tools/call`, an `isError` result and an unknown-tool -32602 all worked (Observed, `ts-dual-auto.log`). Legacy path, observed with the spike's legacy-only mode: Claude Code fell back in the same process (discover, -32601, `initialize` 2025-11-25 id 0, `notifications/initialized`, `tools/list`, "Connected"; `cc-legacy/frames.log`), and TS client 2.4.0 probed in a separate process and then negotiated 2025-11-25 (`ts-legacy-auto.log`, `ts-legacy-auto2.log`). In TS client 2.4.0, a malformed DiscoverResult or a non--32022 error on the `server/discover` probe makes the client fall back to legacy (Observed, `dist/public-CvV4ZHkX.mjs:2040-2104`, `classifyResult`/`classifyRpcError`, read-only). That fallback happens only while the probe is classified; even there an unusable reply is an error (`EraNegotiationFailed`), not a fallback, and nothing shows a fallback when a later modern `tools/list` or `tools/call` result is malformed after 2026-07-28 was negotiated. The mitigation for list and call defects is the M6 exact-frame shape sweep (ADR-001). Whether Claude Code also falls back after a malformed modern response was not tested (Open question). DeepSeek Harness pins client 2.2.0 with automatic negotiation (Observed, `<spike>/host-compat/dsh/package.json` and the 2026-09-12 negotiation note); that 2.2.0 behaves like 2.4.0 is an Assumption. Not observed: a model-driven `tools/call` in Claude Code in either era, and -32022 from a real host.
- **Consequences.** Both observed hosts take the modern path against this server (Observed), so the hand-rolled modern code is the primary path in practice and the legacy code is the fallback for legacy-only clients. Both eras share one frame reader, one dispatcher and one tool adapter; the era changes only `_meta` validation and result stamping. The conformance claim is larger: three revisions across two eras, tracked by hand (ADR-001). The upgrade-lag question for a later legacy-to-dual change (trade-off matrix row "Host compatibility", D column) is moot. Effort: about 35-40 more production lines and about 6 more transcript cases than legacy-only, 0.25-0.5 day (Estimate); this is already inside A's 9-13 day figure, which assumed dual-era (trade-off matrix row "Effort"). The matrix's A-legacy row says "about 30 fewer lines"; that was the option-generation figure, and 35-40 is the re-estimate after the schema-checked dual-era spike (`_meta` validation, -32022 data, result stamping), which is the figure shown to the owner (Estimate).
- **Reversibility.** All era handling sits in the protocol layer behind the `(method, params) -> Result<Value, Value>` boundary (ADR-005). Removing the modern path again means deleting its branch and its transcript cases; removing the legacy path after a future deprecation is the same kind of deletion. An SDK swap (ADR-001) stays contained by the same boundary. A TS-client host falls back to legacy on its own only when the `server/discover` probe returns a malformed DiscoverResult or a non--32022 error (Observed for 2.4.0); a defect in a modern list or call result is not covered by that fallback, so M6 (ADR-001) guards it.
- **Reopen if (triggers).** (1) A new protocol revision is published: add it to MODERN only after its schema is checked; until then requests naming it get -32022, which tells the client to pick 2026-07-28. (2) The spec deprecates the `initialize` era or 2025-11-25: plan removal of the legacy path within the deprecation window. (3) A host's modern or legacy path regresses at a manual host check (AC-003). (4) The modern path proves non-conformant in a way that cannot be fixed cheaply: fall back to legacy-only by deleting the modern branch, with owner consent, since this is an owner decision. Re-check these at every manual host check.

## ADR-005 Framing, lifecycle, per-request era detection and process behaviour

- **Context.** AC-004 requires that stdout carries only protocol frames, that diagnostics go to stderr, and that no network listener opens. The 2026-07-28 stdio page says messages "MUST NOT contain embedded newlines", that the server "MUST NOT write anything to its stdout that is not a valid MCP message", and that the server exits on EOF (Observed 2026-11-27). DeepSeek Harness's SDK starts a disposable probe process (Observed in docs; TS client 2.4.0 frames show two pids per connect). The earlier hand-rolled spike exited silently on one `0xFF` byte, because `let Ok(line) = line else { break }` at `src/main.rs:101` ended the session (Observed, `<spike>/threat-researcher`). The dual-era decision spike has the same pattern (`<spike>/decision-facilitator/srv/src/main.rs:121-122`, Observed), so it is evidence for host behaviour only, not for framing. The owner's dual-era decision (ADR-004) needs a per-request era rule: 2026-07-28 is stateless, with version and capabilities on every request, while the legacy era is stateful through `initialize`.
- **Decision.**
  1. One UTF-8 JSON-RPC 2.0 message per line. Responses are compact `serde_json`, which never contains a raw newline. The main loop is the only stdout writer: one write plus flush under the stdout lock per response.
  2. A bounded byte reader (`take(MAX+1).read_until(b'\n')`) drains the rest of an oversized line. The per-line cap is 1 MiB (Estimate; confirm against the largest legitimate report payload in implementation-design). An oversized line gets -32600 with id null, and invalid UTF-8 gets -32700 with id null. In both cases the session continues. Strip a trailing `\r`, and ignore blank lines. Keep `serde_json`'s default recursion limit of 128 and never enable `unbounded_depth`. Observed in the threat spike: 100k nested arrays gave "recursion limit exceeded" with no stack overflow, and a 5 MiB line and a bad-UTF-8 line were skipped while serving continued.
  3. Requests are processed sequentially and synchronously. Messages with no id are notifications and get no reply. `notifications/cancelled` is ignored, because calls are synchronous. Ids are echoed verbatim, whether string or number. An id of null, a JSON array (batch), a non-object, or a missing or wrong `jsonrpc` value gets -32600.
  4. **Era detection, per request** (owner dual-era decision, ADR-004). The session holds one flag, `initialized`, set by any successful `initialize`. Modern requests never read it. The key below is `params._meta["io.modelcontextprotocol/protocolVersion"]`.
     - (a) `initialize` is always legacy, whatever its `_meta` (ADR-004 rule 1).
     - (b) **Key present (any value): modern**, before or after `initialize`. `_meta` is validated before the method is dispatched and before any project access: a non-string version, or an absent or non-object `io.modelcontextprotocol/clientCapabilities`, gets -32602 (message names both keys; `data: {supported: ["2026-07-28"]}`); a string version not in MODERN gets -32022 with `data: {supported: ["2026-07-28"], requested: <the string, verbatim>}`. Only then is the method dispatched: `server/discover`, `tools/list` and `tools/call` are served; `ping` and unknown methods get -32601.
     - (c) **Key absent, after `initialize`: legacy.** `ping`, `tools/list` and `tools/call` are served with legacy shapes; every other method, `server/discover` included, gets -32601.
     - (d) **Key absent, before `initialize`.** `ping` gets `{}`, because the legacy lifecycle allows pings before initialization. Every other method (`tools/*`, `server/discover`, unknown) is treated as a modern request missing its required `_meta` and gets -32602 "Send initialize (supported: 2025-11-25, 2025-06-18) or include _meta io.modelcontextprotocol/protocolVersion and io.modelcontextprotocol/clientCapabilities (supported: 2026-07-28)". This replaces the legacy-only -32600 "Server not initialized". It deviates from the spike in one place: the spike answered a pre-initialize `ping` with -32602 (`srv/src/main.rs:62-64`, Observed). Neither Claude Code 2.1.332 nor TS client 2.4.0 sends such a request (Observed).
     - (e) **Notifications** get no reply in either era, whatever their `_meta`. `notifications/initialized` and `notifications/cancelled` are accepted and ignored. Notifications are not validated: `NotificationMetaObject` carries no protocol-version key (Observed, schema.json 2026-07-28), and a reply is not allowed anyway.
     - (f) **Result stamping.** After the handler returns `Ok`, the dispatcher adds `resultType: "complete"` and `_meta: {"io.modelcontextprotocol/serverInfo": {name, version}}` to every modern result; `server/discover` and `tools/list` also carry `ttlMs: 0` and `cacheScope: "private"` (ADR-004 rules 6-8). Legacy results get none of these. Error responses get none in either era.
  5. Nothing is written to stdout or disk at startup, or in the `initialize`, `server/discover` and list handlers. The server exits 0 on stdin EOF (Observed: empty stdin gives exit 0 with zero stdout bytes). An invalid `--project` prints to stderr and exits non-zero before reading stdin (AC-004). Engine materialisation happens only inside `next` and `report`, as on the CLI path today.
  6. Each dispatch is wrapped in `std::panic::catch_unwind`. A panic becomes -32603 "Internal error" with no detail, and the default panic hook still writes to stderr only (AC-011).
  7. Protocol error codes:

     | Code | Used for | Era |
     |---|---|---|
     | -32700 | Parse error, invalid UTF-8 (id null) | both |
     | -32600 | Invalid request envelope (null id, batch, non-object, wrong or missing `jsonrpc`); oversized line (id null) | both |
     | -32601 | Unknown method, with the key or after `initialize` (keyless before `initialize` it is -32602, rule 4d); a modern `ping`; `server/discover` without the modern key after `initialize`; `resources/*`, `prompts/*`, `completion/complete`, `subscriptions/listen` | both |
     | -32602 | Unknown tool name; `tools/call` without a string `name`; params or `arguments` that are not objects; `initialize` without a string `protocolVersion`; a modern request with a non-string version or an absent or non-object `clientCapabilities`; a request other than `ping` without the modern key before `initialize` | both |
     | -32022 | Modern request naming a string version not in `["2026-07-28"]`; `data: {supported, requested}`, both required (Observed, schema.json 2026-07-28) | modern |
     | -32603 | A caught panic | both |

     Do not use -32002 (reserved: "never reused"). In the MCP-reserved range -32020..-32099 only the spec-defined -32022 is used: -32020 (header mismatch) is HTTP-only, and -32021 (missing required client capability) never applies because the server requires none. The implementation-defined range -32000..-32019 is unused in v1. Every other failure is a tool-execution result (ADR-008). Observed: schema.ts 2026-07-28 error section (lines 410-530).
  8. Stdout purity needs no library change. A grep of `rust-cli` on 2026-11-27 found no `print!`, `println!`, `eprint!`, `eprintln!`, `dbg!` or stdout use reachable from the four operations. The library hits are all in `#[cfg(test)]` modules (audit.rs:386, 406, 426, 498; workflow/mod.rs:2339), except dependencies.rs:1204 (stderr), which only the CLI `repos` command reaches (Observed). stdin is read only in main.rs, and the MCP binary never calls the main.rs printing or `intent_text` helpers.
- **Status.** Recommended - pending gate approval. That both eras are served is owner-decided (ADR-004); how each request is classified is this record's recommendation.
- **Alternatives.** Use std `lines()` as the spikes did: rejected, since one bad byte ends the session (TH-09) and line length is unbounded (TH-07). Let a panic kill the process and have the host restart it: rejected as the primary path, because a visible server crash looks like R18 to the user; it remains the fallback if `catch_unwind` cannot catch something. Classify every pre-initialize request as modern, including `ping` (the spike's rule): rejected for `ping` only, because a legacy client may ping before `initialize`. Keep -32600 "Server not initialized" for pre-initialize `tools/*`: rejected, because under dual-era such a request is equally a modern request without its required `_meta`, and the -32602 message tells either kind of client what to send. Fix the session to the first era seen: rejected, because 2026-07-28 is per-request and stateless.
- **Consequences.** About 60 test lines for one child-process purity test. A forced-panic transcript case needs a test-only hook. Era detection and stamping are about 35-40 lines (Estimate, from the spike). Windows CRLF is specified (`\r` stripping) but unexercised (A5, R17).
- **Reopen if.** A host needs concurrent calls or real cancellation, a legitimate payload exceeds the line cap, or a later revision changes how the version is carried per request.

## ADR-006 Facade shape

- **Context.** AC-002 requires one shared behaviour path, and AC-001 a byte-identical CLI. The owner chose a thin shared facade (Option A). The plans proposed `ProjectContext` cached per process plus typed request structs and `AppError` (design s3.1-3.2). The CLI logic sits in main.rs (constraint 1).
- **Decision.** One new library module, `application` (for example `rust-cli/application.rs`), holding:
  - `Caller { Cli, Mcp }` and `Project { root, graph, engine, caller }`, opened fresh on every call. `open(project_path, caller) -> Result<Project, String>` keeps the CLI order: `resolve_like_node`, then `assert_safe_state_dir`, then `external_engine` (ADR-016), then `scope::read_graph`, then the external or embedded engine.
  - `status(&Project, intent_id: Option<&str>)` passes through to `status::status`. `queue(&Project)` calls `unit_commands::run("orchestrate queue", ...)` with `load_config_unvalidated` and stays read-only (it marks unmigrated state `migration: pending`; AC-007). `next(&Project, &NextOptions) -> Result<NextOutcome, String>`: for `Caller::Mcp` it runs `knowledge_preflight`, then calls `validate_model_config`, `orchestrate_next` and `finish_directive`. `report(&Project, &ReportOptions) -> Result<Value, String>`: the Q18 guard (ADR-013), `load_config_unvalidated`, `orchestrate_report_with_engine`, `finish_report`, and for `Caller::Mcp` the `pendingPrerequisites` field (ADR-012).
  - Argument parsing, `intent_text`/stdin, flag-validation order, `print_json` and exit codes stay in main.rs. The CLI builds `Project` from values main.rs already holds, so its error order cannot move.
  - Fix to the spike: the spike ran `knowledge_preflight` twice on the CLI path (main.rs and `application::next`). The facade runs it only for `Caller::Mcp`. The CLI keeps its call at main.rs:464, so it still runs before `intent_text` and flag validation. The read has no side effects (knowledge.rs:366-380, Observed), but the duplicate is waste.
- **Status.** Owner-decided principle (thin shared facade, part of Option A, User-provided 2026-11-27). Module name, signatures and per-call open are Recommended - pending gate approval.
- **Alternatives.** Plan design s3.1 `ProjectContext` cached per process plus typed request structs: rejected, because it caches stale engine and graph data across calls, adds golden surface, and is not needed now (YAGNI). No facade (Option D): rejected by the owner's Q5 decision ("guard in shared facade").
- **Evidence.** `<spike>/facade-researcher/approach-a.diff` (226 insertions, 56 deletions in 5 files): the full suite stayed at 454 passed / 2 failed, the same two onboarding failures before and after (`before2.fail` and `after2.fail` identical, Observed 2026-11-27, TMPDIR under /private/tmp).
- **Consequences.** About 140 production lines plus about 50 changed in main.rs (Estimate). 1-1.5 days, since the spike exists. Golden risk Low. Root resolution stays lexical (Q16), so design s3.1's "canonicalized" wording is superseded. The facade is also the hook for intent-2 operation telemetry.
- **Reopen if.** A golden differs after routing a command through the facade (route it back and investigate), or intent 2 telemetry needs per-process state.

## ADR-007 Outcome representation and exit code 3 (Q7)

- **Context.** Blocked prints its payload and exits with `BLOCKED_EXIT_CODE = 3` (orchestrate.rs:39). Design s3.2's `Result<Value, AppError>` cannot carry that (problem-statement contradiction 7). `orchestrate::NextOutcome { Directive, Complete, Blocked, Busy }` already exists (orchestrate.rs:263). The Q7 default was a new outcome struct.
- **Decision.** Reuse `NextOutcome`. Add no new type. The CLI keeps its match in main.rs, and the facade never computes an exit code. MCP maps every outcome to a successful tool result (`isError: false`) with `structuredContent = {"outcome": "directive"|"complete"|"blocked"|"busy", "result": <payload>}`. The payload is the CLI's value, unchanged apart from path redaction (ADR-010), so AC-002 parity reduces to an equality test. Blocked has two sources: the prerequisite hold (orchestrate.rs:1719-1745, payload has `needs`) and Stalled with parked or waiting units (orchestrate.rs:1587-1601). Both map to `blocked`, and the payload tells them apart. The `complete: true` payload (`complete_payload`, orchestrate.rs:639) maps to `complete`. None of these is an error.
- **Status.** Recommended - pending gate approval.
- **Alternatives.** A new `Outcome` struct (Q7 default): duplicates `NextOutcome`. Flattening an `outcome` key into the payload: changes the payload and risks key collisions. Blocked as `isError`: rejected, because it is a valid state, not a failure.
- **Consequences.** About 15 adapter lines. No golden risk. AC-001's "blocked outcome keeps its exit code" scenario is unaffected.
- **Reopen if.** A host cannot handle a non-error blocked result, or intent 2 needs a richer outcome kind.

## ADR-008 Error model and tool result shape

- **Context.** AC-011 requires bounded errors with a stable code and actionable text, with no stack traces, secrets or file contents, and no automatic retries. AC-012 needs a recognisable conflict. Library errors are `String` (`OrchestrateResult<T> = Result<T, String>`, orchestrate.rs:34). The plans proposed a typed `AppError` (design s3.2). The 2026-07-28 tools page classes invalid tool arguments as tool-execution errors (`isError: true`), while an unknown tool or a malformed request is -32602 (Observed 2026-11-27). DeepSeek Harness passes only the content text to the model on error and validates `structuredContent` against an advertised `outputSchema` (Observed, `<spike>/host-compat/dsh/tools.ts:168-211`).
- **Decision.**
  - Keep `String` errors. Classify them in the MCP adapter by exact equality against shared `pub const`s, never by substring. The same text exists twice today: the local `changed` in `ensure_unchanged` (orchestrate.rs:1082) and `const CHANGED` in intent_commands.rs:52-53, which intent_commands.rs's own conflict paths return (intent_commands.rs:274, 278, 1061, 1066; Observed 2026-11-27). Hoist it into one `pub const STATE_CHANGED` in `orchestrate` with identical bytes, and make intent_commands.rs use that constant instead of its private copy, so the exact-match classification cannot drift. The facade owns `APPROVER_REQUIRED`.
  - Codes: `invalid_arguments` (adapter schema validation, raised before the project is opened; AC-005); `approver_required` (equal to `application::APPROVER_REQUIRED`; ADR-013); `state_conflict` (equal to `orchestrate::STATE_CHANGED`, `retryable: true`, meaning safe to call again after re-reading state; never retried by the server; AC-011, AC-012); `operation_failed` (every other facade error, including domain, unsafe layout and I/O; `retryable: false`). A caught panic is the JSON-RPC -32603 in ADR-005, not a tool code.
  - Every `tools/call` result is `{content:[{type:"text", text:<compact JSON of structuredContent>}], structuredContent:<object>, isError:<bool>}`. The adapter builds this one shape for both eras. On the modern path the dispatcher then adds `resultType:"complete"` and `_meta["io.modelcontextprotocol/serverInfo"]` (2026-07-28 `CallToolResult` requires `content` and `resultType`; Observed, schema.json), and on the legacy path it adds nothing (ADR-004 rules 4 and 8; ADR-005 rule 4f). `structuredContent` is always a JSON object, because 2025-11-25 schema.json types it as an object while 2026-07-28 allows any value (Observed). On failure it is `{"error":{"code", "message", "retryable"}}`. The message is path-redacted (ADR-010) and bounded to about 1,000 characters (Estimate). No `outputSchema` in v1; add one when payload shapes are frozen, with a transcript test that checks every result against it.
  - Equality is reliable here: `ensure_unchanged` returns the exact text, and every caller propagates it with a bare `?` (`persist_active`, `persist_new`; reached from `next` and `report`; Observed). If a future caller wraps the error, it degrades safely to `operation_failed`, which is not retryable. The other two "no changes were made" messages need no code: "Intent folder ... appeared" is only in `persist_new`, which is unreachable over MCP (ADR-014), and "Intent '{id}' is not the active intent" is formatted, so it maps to `operation_failed` (safe, not retryable).
  - Tighten the existing contains-assertion near orchestrate.rs:4406 to equality with `STATE_CHANGED`, and add an adapter unit test that the constant maps to `state_conflict`.
- **Status.** Recommended - pending gate approval.
- **Alternatives.** Typed `AppError` (plan design s3.2): changes the error type across orchestrate.rs (about 185 KB) or needs a round-trip back to CLI strings, which raises R1. It can come in intent 2 if telemetry needs finer codes. Substring matching on messages: fragile. JSON-RPC -32602 for argument validation: contradicts the tools page and hides the message from DSH's model.
- **Consequences.** No CLI bytes change. About 4 lines for the constant and the intent_commands.rs switch, about 25 for the classifier and about 30 test lines (Estimate). Domain and I/O failures share `operation_failed`. If AC-011 is read as requiring a distinct I/O code, a small addition is needed (Open question, owner awareness; scope-boundary.md F4).
- **Reopen if.** A host or intent 2 needs finer error codes, or the owner reads AC-011 as requiring a separate I/O code.

## ADR-009 Tool names, input schemas and annotations

- **Context.** AC-003 says the server "lists exactly the tools status, queue, next and report". The Q9 default and the plans use `aidlc_status`, `aidlc_queue`, `aidlc_next`, `aidlc_report` (design s4.3 headings, plan s3.3 table, plan line 386). Both hosts qualify tool names by server: Claude Code shows `mcp__<server>__<tool>` (Observed in docs, solution-options section 2), and the DeepSeek Harness bridge keeps server-qualified names with a 64-character `[A-Za-z0-9_-]` limit (Observed in docs). AC-005 requires strict validation before project access.
- **Decision.**
  - **Names: `status`, `queue`, `next`, `report`.** These match approved AC-003 word for word, so no AC wording changes. An `aidlc_` prefix would only produce `mcp__aidlc__aidlc_next`. This departs from the Q9 default and the plans' names, and it is recorded in scope-boundary.md for owner awareness.
  - **Schemas.** Each tool has an `inputSchema` with `type: object` and `additionalProperties: false`, validated in the adapter before the project is opened. `status`: optional `intent_id`. `queue`: no fields. `next`: optional `claim` (boolean) and `unit` (string); both together are rejected with the CLI's wording (main.rs:485-487). `report`: `stage`, `result`, `detail`, `approval`, `approved_by`, `approval_note`, `needs[]`, `unit`, mapped 1:1 to `ReportOptions` (orchestrate.rs:249-258). Excluded everywhere: `root` or any project path (AC-012), intent text, `scope`, `depth`, `mode`, `force_resume`, and artifact or evidence fields (AC-009). An excluded field gets an `invalid_arguments` result, not -32602.
  - **Caps (envelope; exact numbers are Estimates for implementation-design).** Every string and list is bounded. Starting points: `intent_id` matches the existing safe-id rule (`[a-z0-9-]`, at most 64; status.rs:20-27); `needs` items follow `valid_name` (at most 32 bytes, `[a-z0-9-]`, prerequisites.rs:279-287), with at most 16-32 items; `detail` about 16 KiB; `approval_note` about 4 KiB; `approved_by` 1-200 characters (same as identity.rs:43-44); `stage` and `unit` short and pattern-checked, with the stage format verified against `core/data/phase-graph.json` first. The caps are MCP-only. The CLI has none for `detail` or `approval_note`, and adding them there would change CLI behaviour.
  - **Annotations.** `status`, `queue`: `readOnlyHint: true`. `next`: `readOnlyHint: false`, `destructiveHint: false`. `report`: `readOnlyHint: false`, `destructiveHint: true` (a gate decision cannot be undone over MCP). All four: `openWorldHint: false`. These are static fields in `tools/list`. The spec says clients must treat annotations from untrusted servers as untrusted, and applications SHOULD present confirmation prompts (Observed, 2025-11-25 tools page). Whether Claude Code or DSH act on these hints is an Assumption.
  - **Descriptions.** The `report` description says the approver label is self-asserted and is not authentication (AC-010), and that `approval` should be set only when the human owner decided in the current conversation. The `report` description also says `pendingPrerequisites` is a preview (ADR-012).
- **Status.** Recommended - pending gate approval.
- **Alternatives.** `aidlc_*` names: would need an AC-003 wording follow-up. No annotations: leaves hosts no hint for confirmation prompts (TH-05). Reusing the domain validation only (graph lookup, ledger, `require_known_prerequisites`): stops traversal but leaves sizes unbounded (R15).
- **Consequences.** Generic names could collide in a host that does not qualify by server; both supported hosts do. Intent-2 wireframes that show `aidlc_next` use the plain names instead.
- **Reopen if.** An owner-added host does not namespace tools, or the owner prefers the plan names (then AC-003 needs a wording change).

## ADR-010 Path form in MCP output (Q8)

- **Context.** AC-006 forbids absolute paths at any nesting level of status output, and AC-008 needs directive paths relativised or omitted. Observed: status `intentDir` is absolute (status.rs:189-203). Directives carry absolute methodology paths (orchestrate.rs:966, 985, 997, 1018). `materialize_embedded_engine` returns a canonical path (orchestrate.rs:151), while the root is lexical (orchestrate.rs:381), so on macOS the engine path is under `/private/var` while the root is under `/var`. `knowledge_template_path` uses the raw, unresolved `DTECH_AIDLC_HOME` (knowledge.rs:895). I/O errors embed `path.display()` throughout. The plans disagree: plan s3.3 says include artifact paths, design s4.3 says redact or relativise (contradiction 3).
- **Decision.** One redaction pass, in the MCP adapter only, over every string value and every object key at any depth of each `structuredContent` (success and error), and over every error message before truncation. The text block is the serialisation of the redacted value. Replacements, longest prefix first, each boundary-checked so `/a/b` does not match `/a/bc`:
  1. The project root fixed at launch, in its lexical and canonical forms: `<root>/x` becomes project-relative `x` with forward slashes, and a bare root becomes `.`. The embedded engine therefore becomes `.aidlc/engine/methodology/...` and status `intentDir` becomes `.aidlc/intents/<id>`.
  2. `DTECH_AIDLC_HOME`, in raw and resolved forms (both canonical and lexical): becomes the literal `$DTECH_AIDLC_HOME`.
  3. The user's `HOME`, both forms: becomes `~`.
  4. Last-resort check: any remaining string that still looks absolute (starts with `/`, `[A-Za-z]:[\\/]` or `\\\\`) is replaced. Inside an error message, the whole message becomes the generic text for its code; in a value, the string becomes `<redacted-path>`.
  Methodology paths are rewritten, not omitted, because the agent must read the files a directive names. The docs state that paths are relative to the launch root.
- **Status.** Recommended - pending gate approval.
- **Alternatives.** Omit fields that cannot be relativised (the Q8 default): breaks directives. Redact in the facade: changes CLI bytes. Lexical-root prefix only: misses canonical engine paths on macOS.
- **Consequences.** About 40 lines plus a test that walks success and error values of all four tools and asserts no string contains the root, the canonical root, `HOME` or the engine home. Cases: a project under the default macOS TMPDIR `/var/folders` (symlinked to `/private/var`); `DTECH_AIDLC_HOME` set to an external engine; an I/O error forced with an unreadable `state.json`; a unit test of the Windows-form matcher. Residual: paths in unexpected free-text forms (UNC, `\\?\`) are caught only by step 4. Whether hosts read files given `$DTECH_AIDLC_HOME/...` or `~/...` correctly is unverified (Assumption); the common embedded-engine case is project-relative.
- **Reopen if.** A host cannot open the relative or placeholder paths in directives, or a new output field carries paths in a form the matcher misses.

## ADR-011 Q5 prerequisite guard

- **Context.** Q5 (owner, 2026-11-27): MCP `next` and `report` never run prerequisite shell checks. They return pending prerequisites marked not executed. The guard lives in the shared facade, off for the CLI, and the CLI stays byte-identical. `run_prerequisites` is called only inside `orchestrate_next`, at orchestrate.rs:1470 (claim loop), 1544 (held-unit routing) and 1694 (stage preflight plus blocked needs). `force_resume` does not gate execution (constraint 10). `prerequisite_results` (orchestrate.rs:1054) copies only `name`, `ok` and `exitCode` into the audit. Prerequisite children inherit stdin (prerequisites.rs:171-175; N1).
- **Decision.**
  - Add `NextOptions.skip_prerequisite_checks` (default false). Only `application::next` sets it, for `Caller::Mcp`. Route all three sites through one `check_prerequisites(root, config, names, skip)`. With `skip == false` it is exactly `run_prerequisites`. With `skip == true` it spawns nothing and returns one row per distinct name: a declared name gives `{name, ok:false, hint, exitCode:null, executed:false}`, and an undeclared name gives `{name, ok:true, hint:null, exitCode:null, undeclared:true, executed:false}`. This restores the `undeclared` key the spike dropped. The undeclared skip row is not byte-equal to the CLI's row: the CLI row also carries `"check": null` (prerequisites.rs:263-270), which the skip row drops. The audit is still equal, because `prerequisite_results` copies only `name`, `ok` and `exitCode` (orchestrate.rs:1054-1068). Skip rows omit the owner's `check` command text, so command lines (which may contain paths or tokens) never leave the process over MCP (AC-011).
  - **Semantics: fail-closed.** A check that never ran counts as failing. Site 1470: the unit is not claimed. Site 1544: the next ready unit is used, or the call falls through to site 1694. Site 1694: the call returns Blocked.
  - **Where "returned marked not executed" (AC-008, Q5) surfaces, per site.** The skip rows are internal at sites 1470 and 1544 and are not returned there. At site 1470 the rows only feed the warning string (orchestrate.rs:1470-1490). At site 1544 they only feed `held_checks`, which go to the audit (orchestrate.rs:1566-1571, 2009-2010), and that audit write is suppressed under skip (below). At these two sites the AC-008 channel is the directive's `warnings` array (orchestrate.rs:1580, 955): the warning names each not-executed prerequisite and says "its check is not run over MCP". If site 1544 finds no alternative unit, it falls through to site 1694. At site 1694 the rows are returned in the Blocked payload's `needs` with `executed:false`. Report returns its rows in `pendingPrerequisites` (ADR-012).
  - **Audit under skip.** No `prerequisite.checked` row is written on the site-1694 Blocked path (orchestrate.rs:1700-1706), and site-1544 held checks are not pushed to the row at :2009-2010. A not-executed row would look the same as a real failed check, and the audit schema must not change (non-goal, constraint 12). The success-path row at :2010 still appears when every name is undeclared, and it is then byte-equal to the CLI's.
  - **Hint wording (skip only; the CLI text stays byte-identical).** Site 1694: "Stage {id} needs {name (hint), ...}; prerequisite checks are not run over MCP (not executed). Ask the owner to run 'dtech-aidlc orchestrate next' in a terminal, which runs the checks." Sites 1470 and 1544: replace "and the check is failing" with "and its check is not run over MCP". The prerequisite names stay in the text, as on the CLI.
  - **N1 (child stdin).** No change in intent 1. The MCP server spawns zero child processes: Q5 removes every `sh` spawn on the tool paths, and ADR-013/ADR-014 make the git lookup in identity.rs unreachable. Setting stdin to null for CLI children would change CLI behaviour. N1 is moot for MCP and listed as a CLI follow-up.
- **Status.** Owner-decided principle (Q5, User-provided 2026-11-27). Fail-closed semantics, row shape, the per-site output channel (`warnings` at sites 1470 and 1544, `needs` rows at site 1694), audit suppression, hint wording and N1 handling are Recommended - pending gate approval.
- **Alternatives.** Fail-open (advance without checking): rejected, because it bypasses an owner-configured environment gate, and AC-009's rationale is that MCP must not bypass governance. Write `prerequisite.checked` rows with `executed:false`: needs an audit schema change. Set child stdin to null in shared code: changes the CLI.
- **Consequences.** **Usability ceiling (owner awareness):** because `select_next_stage` (orchestrate.rs:557) re-selects the first unfinished stage and preflight is re-evaluated on every `next`, MCP `next` can never hand out the directive for a stage that has preflight prerequisites or whose last blocked report names `needs`. The `was_blocked` branch (orchestrate.rs:1653-1688) adds the last blocked report's `needs` to the names checked. So after an MCP `report result=blocked needs=[x]`, MCP `next` on that stage or unit returns Blocked until a new report clears the block, even after the owner has run the CLI `next`. The owner runs the CLI `next` for such a stage, and the agent can still `report` over MCP. Tests: one fixture per site (1470 claim, 1544 held unit, 1694 preflight and blocked needs), each asserting that no marker file was created (a PATH shim for `sh`, `git` and `cmd`, plus a fixture prerequisite `touch <marker>`) and that no `prerequisite.checked` row was written. Sites 1470 and 1544 assert the not-executed names in `warnings`. Site 1694 asserts `needs` rows marked `executed:false`. Estimate: about 45 production and 150 test lines, 1-1.5 days. Golden risk Low: the `skip == false` path is unchanged by construction, and goldens verify it.
- **Reopen if.** The owner wants MCP to advance through prerequisite stages (plan s3.3 mentions "a separately approved explicit opt-in"); that needs a new owner decision on Q5.

## ADR-012 Pending-prerequisite list on MCP report (AC-009)

- **Context.** AC-009 and constraint 17 require MCP `report` to return the prerequisites that would run when advancing, marked not executed. The CLI report neither runs nor lists them (orchestrate.rs:2986 only checks that `needs` names are known). So this is new work, on the MCP path only.
- **Decision.** After a successful report, `application::report` for `Caller::Mcp` re-reads the state read-only and calls a new `orchestrate::pending_prerequisites(root, graph, config) -> OrchestrateResult<Vec<String>>`. On a cloned state it predicts the stage the next `next` would select: `work_units::select` when there is a ledger, otherwise `select_next_stage` (orchestrate.rs:557). The clone is discarded and nothing is written. The names come from the same rule as site 1694 (orchestrate.rs:1636-1690): the last report's `needs` when the selection was blocked, plus `preflight_names(config, stage)` (prerequisites.rs:118). Extract that `needed` computation into one helper used by both callers, so the two cannot drift. The field `pendingPrerequisites` is always present on MCP report results (an empty array when there are none or when the intent is complete) and absent on the CLI. Each row is the declared-name skip row from ADR-011, `{name, ok:false, hint, exitCode:null, executed:false}`, the same shape as the `needs` rows on `next`'s Blocked result.
- **Status.** Recommended - pending gate approval. Some list is required by approved AC-009. The source rule and shape are the recommendation.
- **Alternatives.** List every declared prerequisite: over-reports and is useless. Take the stage at graph index+1: wrong for work-unit loops and skipped stages. Predict nothing and ask the owner to reopen AC-009: rejected.
- **Consequences.** It is a preview: claim, pinned and parallel branches can make `next` pick a different unit. The tool description says so. Not spiked. The helper extraction from site 1694 needs the golden suite to confirm CLI byte identity. Estimate: about 50-70 lines plus tests, 0.5-1 day.
- **Reopen if.** The preview proves misleading in use, or the owner reopens AC-009.

## ADR-013 Approver handling (Q6, Q18)

- **Context.** Q6 (owner, 2026-11-27): MCP `report` accepts a self-asserted approver label under the CLI gate policy (AI mode accepts only "AI Orchestrator" plus a valid gate-recommendation; human mode refuses "AI Orchestrator"; `allowedApprovers` applies). Q18 (owner, 2026-11-27): an MCP gate approval without an explicit label is refused before any identity lookup, with no git or OS fallback. Observed: `resolve_approver` runs for every decision value, rejected included (orchestrate.rs:3274-3275). An empty label is treated as missing and falls back to git and then the OS user (identity.rs:41, 52-60). A whitespace-only label is trimmed and then rejected with `APPROVED_BY_ERROR` without any lookup (identity.rs:42-45). The identity check rejects only code points at or below 0x1F (identity.rs:44).
- **Decision.**
  - The first statement of `application::report`, for `Caller::Mcp`: when `approval` is present (any value, approved or rejected) and `approved_by` is absent, empty or whitespace-only after trimming, return `APPROVER_REQUIRED` (code `approver_required`). This happens before any state read or write and before `resolve_approver`, so identity.rs's git and OS fallback is never reached. Refusing whitespace uniformly is simpler than relying on the downstream rejection.
  - With a label, the CLI gate path runs unchanged (Q6), including the existing allowlist refusal text ("Approver '{x}' is not allowed ... Allowed: a, b"), which is kept for CLI parity. The model can usually read `config.json` anyway.
  - **Label characters: CLI parity in v1.** The adapter applies only the length cap (ADR-009). It does not add a stricter character policy (bidi, zero-width, DEL, C1), because AC-010 says a named label is "handled exactly as the CLI handles that label". Tightening it for both CLI and MCP is a follow-up for the owner (scope-boundary.md F2).
  - **Audit provenance: none in v1.** `bySource` stays `"flag"` for MCP approvals, as on the CLI. This preserves the audit-row equality in AC-002 and AC-009 and the no-schema-change non-goal. MCP origin can be recorded by intent-2 telemetry or the host's own tool log. Residual: repudiation, Medium (threat model).
  - The `next` schema excludes `approved_by`, and `next` cannot reach the depth-approver lookup at orchestrate.rs:1962 (ADR-014).
  - **Accepted divergence.** The guard returns `approver_required` for any `approval` without a label, including on a stage that is not a phase gate. For the same input the CLI refuses with "Stage X is not a phase gate here; ..." (orchestrate.rs:3027). Both refuse and neither writes anything; only the error differs. This is accepted so that the guard runs before any state read.
  - **Live gate-policy code.** The CLI report path enforces the gate policy in orchestrate.rs: the mode checks and `resolve_approver` at :3273-3285, `ai_approval_problem` (orchestrate.rs:2750-2769, called at :3288), and the allowlist check at :3296-3307. `gate.rs::validate_gate_approval` (allowlist text at gate.rs:91) is a second copy, reached only through `orchestration_policy` and `orchestration_report_validation`, which only tests call (tests/rust_orchestration_policy.rs, tests/rust_orchestration_report_validation.rs; Observed, grep 2026-11-27). CLI-versus-MCP parity tests target the orchestrate.rs path.
- **Status.** Owner-decided principle (Q6 and Q18, User-provided 2026-11-27). Guard placement, coverage of rejected decisions and whitespace, the non-gate-stage divergence, CLI-parity characters and no provenance are Recommended - pending gate approval.
- **Alternatives.** Guard in the adapter schema only: duplicates the guard, and the owner placed Q5-style guards in the facade. Guard only `approval=approved`: a rejected decision would still reach the git fallback. Stricter character policy now: departs from AC-010 wording without owner consent. `bySource: "mcp"`: breaks AC-002/AC-009 audit equality.
- **Evidence.** The spiked test `spike_mcp_gate_decision_without_approver_is_refused_before_io` (in `<spike>/facade-researcher/approach-a.diff`) asserts nothing is written and that the CLI caller is not refused.
- **Consequences.** About 8 lines plus tests. Test with a PATH shim whose `git` touches a marker: `approval` in {approved, rejected} with the label absent, null, `""` or `"   "` gives `approver_required`, no marker, and `state.json` and `audit.jsonl` byte-identical. Residual TH-01 (a model supplying the owner's name on a human-mode gate) stays High and owner-accepted (Q6). The real control is human confirmation at the host. The AC-010 scenario "approval without an explicit label (pending the Ideate decision)" is now settled by Q18 (scope-boundary.md F1).
- **Reopen if.** A host offers server-verifiable consent (the plans' human-approval design), or the owner wants MCP provenance in the audit (needs an AC-009 or AC-002 change).

## ADR-014 MCP next only continues an existing active intent (AC-008)

- **Context.** AC-008: MCP `next` runs only when an active intent exists, and never creates or selects one. Observed: `orchestrate_next` sets `is_new = true` only at orchestrate.rs:1272, when intent text is given, so design s4.3's claim that it creates an intent without text does not match the code (solution-options fact 4). With no active intent it returns "No active intent. Start one with: dtech-aidlc orchestrate next --intent ..." and writes nothing (orchestrate.rs:1189-1208).
- **Decision.** The `next` tool accepts only `claim` and `unit` (ADR-009). As defence in depth, `application::next` for `Caller::Mcp` resets `intent`, `scope`, `depth`, `mode`, `approved_by` and `detail` to `None` and `force_resume` to false before calling `orchestrate_next`. The "No active intent" message, which steers the human to the CLI, maps to `operation_failed`. A finished intent returns outcome `complete`.
- **Status.** Recommended - pending gate approval (the behaviour is required by AC-008).
- **Alternatives.** Reject in the adapter only: no defence in depth. A new "continue-only" entry point in orchestrate.rs: unnecessary.
- **Consequences.** The depth-approver `resolve_approver` call at orchestrate.rs:1962 and the `persist_new` path are unreachable over MCP. About 10 lines plus 2 tests (no active intent writes nothing; a completed intent returns `complete`). No golden risk.
- **Reopen if.** The owner wants intents started over MCP, which would need a new decision covering scope, depth, mode and the depth approver.

## ADR-015 Concurrency without an operation ID (Q10)

- **Superseded by owner decision (User-provided, project owner, 2026-11-28, AskUserQuestion during Develop):** add an advisory file lock now. Evidence that triggered it: WU-007 test `ts007_concurrent_reports_never_lose_an_update` showed two concurrent `report` calls both returning `recorded: true` and appending two `stage.reported` audit rows while `state.json` kept one report (12/12 rounds with an 8 MiB padded state; the window exists for the CLI too). Decision: wrap the check-and-write of workflow state in an advisory, process-exclusive file lock (std `File::lock`, no new crate; MSRV 1.100 has it) so a conflicting second writer gets the retryable `state_conflict` instead of a silent lost update and an audit row for a write that never landed. CLI output is unchanged without contention. Implemented through `intent rework --unit WU-007` with a new work unit minted by implementation-design.
- **Owner decision (User-provided, project owner, 2026-11-27, AskUserQuestion at the solution-direction gate):** accept the documented compare-then-rename window for v1. No lock and no operation ID; a detected conflict is returned once as a retryable `state_conflict` error and never auto-retried; CLI write behaviour is unchanged. AC-012 is met up to that documented window. Adding an advisory lock (std `File::lock`) stays a recorded alternative that would reopen this decision.

- **Context.** A long-lived MCP server and the CLI may write the same project. The only guard is the optimistic `ensure_unchanged` compare-before-write (orchestrate.rs:1071-1091). There is no file lock (A1). State is written temp-then-rename (workflow/mod.rs:1670), and the audit is appended separately with `O_APPEND` (audit.rs:171-193). Design s5 mentions operation IDs, but no schema defines one (contradiction 10), and it states exactly-once is not promised.
- **Decision.** No operation ID and no lock in v1. Re-read state on every call (ADR-006). A conflict surfaces once as `state_conflict` with `retryable: true` (ADR-008) and is never retried automatically. The residual window is documented: the compare-then-rename is not atomic, and both writers append audit. Test deterministically without hooks: the library-level stale-load test asserts equality with `STATE_CHANGED`, a deterministic interleaving test modifies `state.json` between load and persist (pattern: intent_commands.rs `ensure_unchanged_refuses_files_changed_after_load`) and expects exactly one conflict, no partial state and no extra audit row, and an adapter test maps the constant to `state_conflict`. No non-deterministic CLI-plus-MCP race test is added.
- **Status.** Recommended - pending gate approval.
- **Alternatives.** An idempotency or operation ID: not needed now (YAGNI). A file lock: new behaviour on the CLI path, so golden risk.
- **Consequences.** R6 stays Low likelihood, High impact, documented and not closed. AC-012 ("shall not corrupt intent state"; at most one of two conflicting writes succeeds) is met only up to the compare-then-rename window, which is the same window two concurrent CLI runs have today. AC-012's Source lists the sufficiency of the current concurrency check as an owner open question, so this is an owner awareness item (scope-boundary.md F9). That a single short `O_APPEND` write is not torn on a local filesystem is an Assumption (POSIX does not guarantee it for regular files).
- **Reopen if.** A lost update or a torn audit line is observed, or intent 2 needs operation correlation.

## ADR-016 Engine resolution sharing (Q15)

- **Context.** AC-002 scenario "engine selection honoured": both entry points use the same engine. main.rs has a private `external_engine()` (main.rs:403-409). Six library modules read `DTECH_AIDLC_HOME` separately (doctor.rs:119, intent_commands.rs:200, config_commands.rs:67, knowledge.rs:895, ids.rs:567, onboarding/mod.rs:1147; Observed via research), with subtle differences. Observed (main.rs:403-409): when `DTECH_AIDLC_HOME` is set but holds neither `data/phase-graph.json` nor `methodology`, `external_engine()` returns `None` and the CLI silently uses the embedded engine.
- **Decision.** Move `external_engine()` unchanged into `application::external_engine()`. main.rs delegates to it (as spiked), and `application::open` uses it, so both binaries resolve `DTECH_AIDLC_HOME` identically. The other six library copies are not touched. In addition, the MCP binary writes one stderr warning at startup when `DTECH_AIDLC_HOME` is set but unusable. That keeps MCP from falling back silently without changing what either binary selects (stderr only, so AC-004 holds, and CLI bytes are unchanged).
- **Status.** Recommended - pending gate approval.
- **Alternatives.** Unify all seven copies: risks goldens for no intent-1 benefit. Make an invalid `DTECH_AIDLC_HOME` an error in the shared function: changes CLI behaviour (AC-001).
- **Consequences.** About 10 lines (spiked) plus an engine-parity test with `DTECH_AIDLC_HOME` set (AC-002). The CLI keeps its pre-existing silent fallback, which is in tension with the AC-002 phrase "neither silently falls back". The phrase is read here as "neither falls back to a different engine than the other". Owner awareness item (scope-boundary.md F3).
- **Reopen if.** The owner wants the CLI to refuse an invalid `DTECH_AIDLC_HOME` (a CLI behaviour change with a CHANGELOG entry), or engine drift between the library copies is observed.
