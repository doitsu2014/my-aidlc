## 2. Why this direction

The owner chose A over B explicitly (User-provided, 2026-11-27). The evidence below supports that choice. It is not a substitute for it.

- **Q3 compliance with no rulings needed.** A adds zero crates, leaves Cargo.lock unchanged, and keeps clean-cache offline `--locked` install working for both binaries (Observed, packaging spike C1; trade-off matrix row "Q3 dependency compliance": Strong). It is the only protocol-complete option that does this without an owner ruling on whether Q3's offline promise covers the MCP binary (trade-off-matrix Summary, decision 1).
- **Facade, guards and intent-2 fit equal to B.** A and B share the same facade, so their CLI byte risk (Low; the spike kept the suite at 454 passed / 2 failed with an identical failure set, Observed `<spike>/facade-researcher/{before2,after2}.fail`), Q5/Q6/Q18 handling and intent-2 telemetry hook are identical (trade-off matrix rows 3, 5 and 10).
- **Highest reversibility.** The protocol loop sits behind a `(method, params) -> Result<Value, Value>` boundary, and the tool handlers take and return `Value`. An SDK (Option B) can replace it, and either era can be removed later, without touching the facade or the tools (trade-off matrix row "Reversibility": High).
- **Both eras observed in real hosts.** With the dual-era spike, Claude Code 2.1.332 took the modern path (`server/discover` with `_meta`, then `tools/list` with `_meta`, same process) and showed "Connected" (Observed 2026-11-27, `<spike>/decision-facilitator/cc-dual/frames.log`). The official `@modelcontextprotocol/client` 2.4.0 in `auto` mode probed in a separate process and then served on 2026-07-28, and list, call, `isError` results and unknown-tool errors all worked (Observed, `ts-dual-auto.log`). The legacy path was observed with the spike's legacy-only mode: Claude Code fell back from -32601 to `initialize` 2025-11-25 in the same process (`cc-legacy/frames.log`), and TS client 2.4.0 negotiated 2025-11-25 (`ts-legacy-auto.log`, `ts-legacy-auto2.log`). DeepSeek Harness pins client 2.2.0 with automatic negotiation (Observed, `<spike>/host-compat/dsh/package.json`). That 2.2.0 behaves like 2.4.0 is an Assumption; if it does not speak 2026-07-28, the legacy path serves it.
- **Modern-only resilience (owner's choice).** Dual-era keeps working if a host goes modern-only, which was the benefit the owner weighed against about 35-40 more lines, about 6 more transcript tests and 0.25-0.5 day (User-provided, 2026-11-27).

## 4. Residual risks carried into Develop

- **R18 (host compatibility).** DeepSeek Harness has not been run (`dsh` is not on PATH). Claude Code was exercised only through `claude mcp list` (modern discover plus `tools/list` with the dual-era spike; legacy fallback with the legacy-only mode), and no model-driven `tools/call` was observed in either era. Because both observed hosts now take the hand-rolled modern path by default, a modern-path defect is the main R18 exposure. TS client 2.4.0 falls back to legacy on a malformed DiscoverResult or a non--32022 error on the `server/discover` probe (Observed, read-only); no fallback is shown for a malformed modern list or call result, which M6 (ADR-001) guards; whether Claude Code does the same was not tested (Open question). Manual launch-and-list in both hosts, recording the negotiated era, is required for AC-003 before the intent closes.
- **Hand-tracked spec, two eras.** The protocol is ours to maintain across three revisions (2026-07-28, 2025-11-25, 2025-06-18) in two eras. The spec had five revisions in about 20 months, 2026-07-28 was breaking, and a twelve-month deprecation window applies (Observed, changelog). The legacy `initialize` era is not on the deprecated-features registry (Observed, modelcontextprotocol.io/specification/2026-07-28/deprecated, 2026-11-27). The modern-path field requirements were re-checked against the saved 2026-07-28 schema on 2026-11-27 (ADR-004). The conformance burden is about 6 more transcript cases than legacy-only, and a future revision is added only after its schema is checked. The triggers are in ADR-004.
- **Usability ceiling from fail-closed Q5.** Because `next` re-selects the first unfinished stage and re-evaluates its preflight on every call (Observed, orchestrate.rs:557 and 1636-1694), MCP `next` can never hand out the directive for a stage that has preflight prerequisites or whose last blocked report names `needs` (orchestrate.rs:1653-1688); after an MCP blocked report with `needs`, MCP `next` stays Blocked until a new report clears it, even after the owner runs the CLI `next`. The owner runs `dtech-aidlc orchestrate next` in a terminal for that stage (ADR-011). Owner awareness item.
- **R6 (concurrency).** The compare-then-rename window is documented, not closed (ADR-015). AC-012 is met only up to that window, the same as two concurrent CLI runs today (scope-boundary.md F9).
- **Self-asserted approver (R5).** The label is not authentication. The owner accepted this residual (Q6).
- **Untested platforms.** Windows (CRLF, `.exe`, path forms) is untested (A5, R17).

## 5. What the gate approves, and what it does not

Approving solution-direction approves Option A with the owner-decided dual-era protocol as the direction, the owner-decided items above, and the recommended decisions in the decision record as the basis for implementation-design. It does not approve implementation details beyond those decisions (numeric caps, module file names, exact schema text), any release, version bump or publication, any change to install scripts, or any edit to host settings. See [scope-boundary.md](scope-boundary.md) for owner-held items and the follow-ups the owner should be aware of: tool names (AC-003 wording reconciled, no change needed), the AC-010 pending-scenario status, audit provenance, the invalid-`DTECH_AIDLC_HOME` fallback, and the AC-012 concurrency window.
