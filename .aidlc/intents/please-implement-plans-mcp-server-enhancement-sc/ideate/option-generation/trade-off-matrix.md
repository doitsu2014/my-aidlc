## Summary

- **No option dominates on every criterion.** The real choice is between **A** (zero dependencies, offline install intact for both binaries, high reversibility; we own conformance) and **B** (conformance maintained upstream; the cost is about 62 crates, a second lockfile and package, and rmcp release churn). Their facade, guards, stdout purity and intent-2 fit are identical, because they share the same facade.
- **Option C is infeasible under the strict reading of Q3.** CLI offline install was Observed to fail on a clean cache (spike A1). If the owner rules that a networked-primed cache is enough and that a feature-gated SDK in the same package is acceptable, C becomes feasible. Even then B weakly dominates it on CLI dependency isolation and churn exposure, and C only wins on having one lockfile and plan-literal layout.
- **Option D is not compliant with owner decision Q5 as decided** ("guard in shared facade, off for CLI", constraint 17), because it has no facade. Like C under Q3, it is feasible only if the owner rules otherwise. Even then it trades long-term fit for speed: it is the cheapest and has the lowest CLI byte risk, but it is weakest on AC-002 and on intent-2 fit. Its no-facade element is dominated over the life of both intents, because intent 2 must build the facade anyway.
- **Legacy-only versus dual-era is a real choice, not a dominated one.** Legacy-only is the only protocol path observed connecting in a real host (Claude Code reached "Connected" after the -32601 fallback), and it avoids the hand-rolled modern-path R18 risk named in A's row. Dual-era serves modern-only clients and avoids the 7-day re-probe lag on a later upgrade. Variant **A-legacy** (A's facade with D's protocol, about 30 fewer lines) keeps that choice open without D's Q5 problem.
- **Do nothing** fails the intent's stated scope. The facade-only partial variant is a valid staging step, but it does not meet the scope.
- **Decisions that would change the ranking** (for direction-selection or the owner):
  1. Whether Q3's offline-install promise covers the MCP binary. If yes, B carries a residual offline gap, A is the only fully compliant protocol-complete option, and A's ADR can name a concrete blocker (design s4.2, plan Phase 0 step 3). If no, A remains allowed by Q3's ADR clause but departs from those plan clauses.
  2. Whether a guard outside a shared facade satisfies Q5. Only this ruling would make D feasible.
  3. Whether the owner prefers dependency-free code we maintain over an upstream SDK with fast churn. This is the A versus B axis.
  4. Legacy-only (A-legacy) versus dual-era (A), if the hand-rolled route is chosen.
  5. The result of the manual launch-and-list in Claude Code and DeepSeek Harness. It applies to every option and has not yet been run for DSH.
