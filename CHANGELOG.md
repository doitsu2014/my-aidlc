# Changelog

Each release lists the behaviour changes a user or a script can notice.

## 1.3.0

- Added the `dtech-aidlc-mcp` binary, a local stdio MCP server with the tools `status`, `queue`, `next` and `report` over the same library behaviour as the CLI, which is unchanged. The server, telemetry and monitor are local optional capabilities; the CLI works without them. The minimum Rust version is 1.100. Approver names are self-asserted by the host. The README MCP section keeps its "proposed" label: DeepSeek Harness has not been verified against the server, and the label is dropped only after green CI on Windows and macOS and a live Claude Code `tools/call`. This release therefore ships the server as proposed: the MCP server, telemetry, monitor and installers are released; the live host verification (Claude Code `tools/call`, DeepSeek Harness, Windows host launch) is still pending.
- MCP telemetry is on by default and MCP-only; start the server with `--telemetry off` to record nothing. Events go to `.aidlc/telemetry/` with retention of 5 MiB per file, 7 days and 50 MiB in total. Dropped events are disclosed on stderr, not recorded or counted. The CLI writes no telemetry. Telemetry is not audit. The intent id is made from the first words of the intent text you typed; do not put names or secrets in intent text. The managed `.gitignore` gains a `/telemetry/` line.
- Added `dtech-aidlc monitor`: a read-only dashboard of the MCP telemetry, bound to 127.0.0.1 only, with a per-run token in the URL fragment printed on stderr. Ctrl+C stops it. It adds a `monitor` line to help, completion and validation output.
- The shell and PowerShell installers now install, upgrade and uninstall both binaries, `dtech-aidlc` and `dtech-aidlc-mcp`. `cargo install --path . --locked` installs both.
- `deps add` now takes the `.aidlc` state lock, so concurrent `deps add` runs no longer lose edges.
- Fixed flaky tests (prerequisite timeout, artifact verification, projection backups) and added characterisation tests for the MCP server follow-ups.
- Golden snapshots changed only for the version, the `monitor` help, completion and validation lines, and the `/telemetry/` ignore line.

## 1.2.2

- Harden Claude Code Workflow guidance against JavaScript prompt-quoting parse errors: load the workflow-authoring skill, use ordinary quoted strings for prompts containing Markdown backticks, and correct parse failures before retrying. Added regression checks and recognized the updated skill projection hash.

## 1.2.1

- Fixed Windows prerequisite commands containing quoted paths or arguments: pass the configured check to `cmd.exe` without Rust's C-runtime argument escaping, preserving `cmd`'s native parsing. Unix shell invocation is unchanged. A Windows-only regression test checks a quoted path containing spaces and `&`, plus a quoted executable path.
- Added `orchestrate revisit --confirm --unit <id> --approved-by <owner>` to record a human owner's confirmation of a closed AI-orchestrator owner decision. Queue, complete and doctor views now distinguish pending from confirmed decisions; confirmation emits `unit.decision-confirmed`.
- `orchestrate next --mode` on an active intent now errors if the requested mode differs from its fixed mode; omit `--mode` to resume.
- A work-unit claim now checks stage preflight prerequisites before handing out the unit. A failing prerequisite keeps the unit unclaimed, reports a warning, and does not stop other in-flight work.
- Claude and DeepSeek instructions now explain explicit-depth approvers, AI mode, project-root-relative artifact paths and the required `failures` array in regression evidence. The knowledge-record template now uses `origin: intent`, matching intent-closure validation; AI open-item tags must begin each list item. Onboarding docs describe methodology materialization under `.aidlc/engine/methodology/`.

## 1.2.0

Parallel work units: up to `unitWorkers` work units (default 3) can be in flight at once. Intents that never claim behave exactly as in 1.1.0.

- New configuration key `unitWorkers` (positive integer, default 3) in `.aidlc/config.json`, validated by `orchestrate next`, `config` and `doctor` like `autoParkThreshold`.
- `orchestrate next --claim` claims one more ready work unit while others are in flight and prints its ordinary directive. A claim only takes a unit whose dependencies are done and that is not in flight. Claims are kept in the new optional `workUnits.claims` list (`[{unit, stage, claimedAt}]`); the current unit stays in `currentStage`/`currentUnit`. With nothing in flight, `--claim` selects like plain `next`. When no unit can be claimed it prints `{"claimed": false, "reason": "workers-busy" | "no-ready-unit", "parallel": …, "hint": …, "warnings"?: …}` and exits 0. It writes only revisits it made, as a stall does.
- `orchestrate next --unit <id>` prints the directive of a unit in flight again, keeping its selection time. Plain `orchestrate next` never claims. While claims exist it resumes the current unit, or promotes the oldest claim when the current unit has left the pool.
- `orchestrate report --unit` and `orchestrate park --unit` accept any unit in flight. `--unit` is required on a report or park while any claimed unit is in flight. A claimed unit's stage preflight checks run before it is handed out; a failing check leaves the unit unclaimed and returns the usual `claimed: false` result with a warning instead of stopping the whole intent. During a parallel run (the new `workUnits.parallelSince`, set at the first claim and removed once nothing is in flight), a unit reported complete or skipped on `red-tests` stays in flight on `build-and-verify`, and plain `next` resumes the current unit instead of re-selecting. A unit leaves the pool when its last step is reported, when it is reported blocked, when it is parked, or when it can no longer run. Parking a claimed unit counts its attempt. `--claim` makes the automatic and drain revisits that plain `next` makes, and without a current unit it first promotes the oldest claim.
- Freshness: a unit's `regression.json` must be written after both the step's selection and the ledger's new `lastSatisfiedAt`, the last time any unit became satisfied during a parallel run. `lastSatisfiedAt` is only stamped during a parallel run, so an intent that never claims gets no new key and no new check. With several, every unit is verified on a tree that holds every finished unit's code.
- Unit directives and `orchestrate queue` carry a `parallel` view (`workers`, `inFlight`, `free`; directives add `claim`), and unit report outputs add `parallel.continues` (the step the unit stays in flight on, or null). `stage.selected` audit rows of a claimed unit carry `claim: true`.
- Claude Code skill: a new Parallel work units section. It claims up to the free workers, runs one `Workflow` agent per unit in its own worktree, and integrates and verifies the units one at a time in the main tree, committing each finished unit on the intent branch only with the owner's consent. It falls back to one unit at a time when `Workflow`, worktrees or commits are not available. The DeepSeek skill runs one unit at a time.

## 1.1.0

Unit-level scheduling of Develop: work units run in dependency order, blocked units are parked while the others continue, failing tests are attributed to their owning unit, design rework is scoped to the named units, and the release-candidate gate moves to a final regression sweep. The crate version is unchanged.

- Develop's repeating stages (`red-tests`, `build-and-verify`) are scheduled per work unit. An intent whose `work-units.json` lists units gets a work-unit ledger, the new optional `workUnits` key of its `state.json` (`schemaVersion: 1`); the top-level `version` stays 2. The next unit is the first one in `work-units.json` order whose `dependsOn` units are done (`green`, `verified` or `done`), so dependencies, not array order, decide the order. Unit statuses are `pending`, `red`, `blocked`, `green`, `verified`, `done` and `parked`.
- The 1.0.0 keys are kept as mirrors that a 1.0.0 binary can still drive: `stages[s].units`, the status of the repeating stage rows and `state.units`. `red-tests` is complete once every unit finished red; `build-and-verify` stays in progress until the release sweep passes.
- The release-candidate gate moved from the last unit's `build-and-verify` to a final release sweep: a `build-and-verify` directive without `currentUnit`, selected once every unit is done, with `stage.phaseGate: true` and a `sweep` object. `--approval` on a per-unit step is refused, and the sweep cannot be skipped. A 1.0.0 binary sees the last unit as unfinished until the sweep passes, so it stops at its own release-candidate gate.
- In-flight 1.0.0 intents migrate on the first `orchestrate next`, `orchestrate report` or `intent rework`: steps and statuses come from the stage rows, results a 1.0.0 rework reset are kept as `priorResults` (information only), and entries such as the one-unit placeholder `"_"` are left in place and listed in `migration.ignoredKeys`. Only `workUnits` is added, so removing it is a rollback. One `units.migrated` audit row is written; older rows are untouched. An intent whose 1.0.0 design rework is still open migrates when `implementation-design` is reported complete.
- `orchestrate report --unit ID` names the work unit being reported; it must be the current unit, and that unit must still be able to run the current step: a report on a parked, finished or waiting unit, or on a step that is not the unit's next one (for example after a 1.0.0 `orchestrate next` moved only `currentUnit`), is refused with "No current stage; run orchestrate next first" and the reason. Unit reports carry `"unit"` in the stage row, the `stage.reported` and `stage.selected` audit rows and the report output, and keep per-unit attempts and a blocked streak. Directives of a unit step gain `unit` and `queue` objects, and `stage.rework` is per unit (`unit`, `attempt`, `blockedStreak`, `autoParkThreshold`).
- `work-units.json` is loaded strictly when the ledger is built. A missing, unreadable or invalid file is an error that starts with "Develop cannot select a work unit:"; there is no one-unit placeholder any more, and the old "runs as one implicit work unit" warning is gone. `{"status": "not-applicable", "reason": ...}` and fast depth still run Develop as one implicit unit. `intent rework` is accepted when the file cannot be loaded, even when nothing is blocked. After the ledger exists, edits to `work-units.json` or `ids.json` are reported as drift and not applied.
- `work-units.json` units may list owned tests in `"tests": ["TS-01", ...]`; reporting `implementation-design` refuses ids that are not `TS-` identifiers or not registered in `ids.json`.
- `status` shows a `units` summary (counts by status and one row per unit with its next step), as a read-only preview with `"migration": "pending"` before the ledger is stored. `intent list` rows of ledger intents gain `workUnits`. `doctor` accepts any repeating stage as current once the stages before Develop's repeat span are finished (red-tests of one unit and build-and-verify of another interleave), fails on a `work-units.json` that cannot be loaded, and warns about drift and about placeholder entries.
- Fix: a design rework requested after `implementation-design` was itself reported blocked is consumed when that stage is selected again; previously the pending request survived and made Develop fall back to one implicit unit. The directive's `stage.rework` then carries the request (`requestedAt`, `fromStage`, `detail`).
- `intent rework [--unit ID]... --detail TEXT` on a ledger intent records the request in the ledger (`workUnits.rework`, with each unit's `inputFingerprint`) and keeps `state.units` and every unit entry. With `--unit` (repeated or comma-separated, `U-01` and `WU-01` name the same unit) one of the named units must be blocked or parked, or the last release sweep report must be blocked (a red sweep or a rejected release gate); without `--unit` any blocked or parked unit, a blocked sweep or the 1.0.0 condition is enough. A second request while one is pending is refused, `implementation-design` cannot be reported `skipped` while one is pending (only `complete` reconciles it), and `--unit` on an intent without a ledger is refused. The output, `state.designRework` and the `design.rework.requested` audit row carry `units`. The `implementation-design` directive's `stage.rework` carries `units` and an `instruction` to change only the named units' rows and sections.
- When `implementation-design` is reported complete after a ledger rework, the units are reconciled by fingerprint (the unit's `work-units.json` row, its `## <id>` section of `work-units.md` without `Status:` items, and the cited registry entries): only the named units, units whose fingerprint changed, and their direct dependants that had a finished or blocked step are reset to `pending` (history kept, a `reopened` row with `by: "rework"`). A changed unit's open park is closed; a reset dependant keeps its park and resumes as `pending`. New ids are added as `pending`, missing ids are kept as `removed`, and every other unit keeps its status with no report appended, so finished units are not replayed with skip reports. `units.reconciled` lists `kept`, `reset`, `added`, `removed` and `changed`. A green sweep goes back to pending when anything was reset, added or removed.
- New `intent split ID --into ID... --detail TEXT` replaces a work unit that is not finished with at least two units through `implementation-design` (audit `intent.split.requested`, output `splitRequested`). `--into` may keep `ID`; new ids must not name another unit, removed ones included. At the `implementation-design` complete report every `--into` id must be listed in `work-units.json` and `ID` must be gone unless it is in `--into`, otherwise the report is refused with nothing written. The `--into` units are reset or added, a dropped `ID` is kept as `removed` with `splitInto`, and the other units are kept.
- A ledger that an older dtech-aidlc changed afterwards is re-synced by the next `orchestrate next`, `report`, `park`, `revisit`, `intent rework` or `intent split` (and shown re-synced by the read-only `queue`, `status` and `doctor`). A stage entry reported after `workUnits.syncedAt` re-derives that unit's step; a 1.0.0 `intent rework` (its `designReworkPending` marker, or a newer `reworkRequestedAt`/`reworkResetAt`) becomes a ledger rework with no named units and, when 1.0.0 already completed `implementation-design`, is reconciled by fingerprint at once instead of resetting every unit; a release-candidate gate that 1.0.0 approved on the projected gate unit is accepted as the sweep (`sweep.via: "1.0.0-gate"`, every unit `done`). Audit `units.resynced` (`units`, `legacyRework`, `legacyGate`), plus `units.reconciled` when a redesign was reconciled.
- New `orchestrate park [--unit ID] --kind dep-unit|foreign-regression|owner-decision|design-defect [--blocked-by ID]... --detail TEXT` sets a blocked work unit aside with a structured reason; `orchestrate next` then continues with the next ready unit. `--unit` defaults to the current unit. `dep-unit` names the units it waits for; `foreign-regression` names failing `TS-` tests (resolved to their owning units through `work-units.json` `tests` and `ids.json` traces) or units; `owner-decision` and `design-defect` may name decision ids such as `CFG-17`. A park is refused when a blocker depends on the parked unit (an inverted dependency), when every blocker is already done, when it would close a wait cycle with other parks, while a design rework is pending, and before Develop reaches its work units. An environment problem stays `orchestrate report --result blocked --needs NAME`; it holds only that unit: while the named check fails, `orchestrate next` runs the next ready unit instead (a `Work unit ... is held` warning, and a `prerequisite.checked` audit row with `unit`), and holds the unit with exit code 3 only when no other unit can run. A park appends a `blocked` report with `"parked": {kind, blockedBy, auto}` and audits `unit.parked`; parking right after a blocked report does not count a second attempt.
- New `orchestrate queue` (read-only) lists ready, waiting, blocked, parked and done units, the sweep status, owner decisions, drift and `priorResults` (`{unit, stage, result, at}` rows recovered by the migration); before a 1.0.0 state migrates it shows a preview marked `"migration": "pending"`.
- New `orchestrate revisit [--unit ID]... [--detail TEXT] [--approved-by NAME]` returns parked units to the queue. Without `--unit` only `dep-unit` and `foreign-regression` parks whose blockers are done come back. An `owner-decision` park needs `--detail` (the decision), and the decider is recorded by the gates' mode rule: in a human-mode intent `--approved-by` (else the git or OS user), in an AI-mode intent always "AI Orchestrator" (another `--approved-by` is refused); an "AI Orchestrator" decision is listed as unconfirmed; a `design-defect` park is cleared only by `intent rework`. Each revisit audits `unit.revisited`.
- `orchestrate next` revisits parked units on its own: a `dep-unit` or `foreign-regression` park comes back as soon as every unit it waits for is done (`blocker-done`), and, when nothing else is ready, once per progress event even if its blockers are not done yet (`drain`). The revisited unit resumes at its blocked step, and `stage.rework.revisit` / `unit.revisit` describe the park it came from. When no unit can run, `orchestrate next` exits with code 3 and prints `{"blocked": true, "reason": "queue-stalled", "parked": [...], "waiting": [...], "hint": ...}`; revisits made by that call are saved, otherwise nothing is written.
- `orchestrate revisit --confirm --unit <id> --approved-by <owner>` records a human owner's confirmation of a closed AI-orchestrator owner decision. `queue`, the complete payload and `doctor` distinguish pending from confirmed decisions; `unit.decision-confirmed` is audited.
- `orchestrate next --mode` on an active intent now errors if the requested mode differs from the intent's fixed mode; omit `--mode` to resume.
- Claude and DeepSeek harness instructions now explain explicit-depth approvers, AI-mode setup, project-root-relative artifact paths and the required `failures` array in regression evidence. The knowledge-record template uses `origin: intent`, matching intent-closure validation; AI open-item tags must begin each list item. Onboarding docs describe methodology materialization under `.aidlc/engine/methodology/`.
- Auto-park: the third consecutive `--result blocked` report of the same unit and step (without `--needs`) also parks the unit as `owner-decision` with `auto: true`; the report output gains `"parked": {"kind": "owner-decision", "auto": true, "count": 3, ...}`. The number is `autoParkThreshold` in `.aidlc/config.json` (a positive integer, default 3); `orchestrate next`, `config agents` and `doctor` reject other values (`config scope` and `config mode` do not validate it, as for `unitSplitThreshold`), and `orchestrate report` falls back to 3. Reports with `--needs` never count.
- `intent rework` is also accepted when a work unit is parked; the reconcile at `implementation-design` complete closes the open parks of the units it resets as changed (`revisitReason: "rework"`).
- The fallback error for an unknown `orchestrate` action reads "Use orchestrate next, report, park, queue or revisit".
- Attributed regression: `--result complete` on a work unit's `build-and-verify` (ledger intents) needs a `regression.json` beside the unit's regression report (`.aidlc/intents/<id>/develop/build-and-verify/<WU>/regression.json`, named by the directive's new `verification` object). It records the run (`schemaVersion: 1`, `unit`, `scope: full|affected`, `commands`, optional `summary`, and `failures` with `test`, `suite`, `ts`, `owner`, `baseline`). The file must be a regular file written after the step was selected; an invalid, stale or missing file refuses the report and writes nothing. Selecting the step that is already current again keeps its selection time.
- Each failure is attributed to an owning work unit: the explicit `owner` (which must own the test's TS ids when the work units declare them), else the owner of the TS id given in `ts` or read from the test name (`ts27a_…` gives `TS-27`), else the reporter when no work unit declares any tests. Failures owned by the reporter or by an already finished unit refuse `complete`, with the list. Failures owned by an unfinished unit are deferred and failures without an owner are recorded as unowned; neither blocks the unit. Both go to the new `workUnits.deferredRegressions` record (open/resolved, first/last seen, reporters), and declared baseline failures go to `workUnits.baselineTests`. A `full` run resolves the open items it no longer lists, and a full run without failures outside the baseline upgrades every `green` unit to `verified`. Each accepted run audits `regression.attributed`, and the report output gains a `regression` object.
- The release sweep needs a fresh full `regression.json` with `"unit": "sweep"` in `.aidlc/intents/<id>/develop/build-and-verify/`, no failure outside the baseline, and no baseline failure that an earlier unit run did not declare; a parked unit (its status, or a park record still open) refuses the gate with its own error. A `regression.json` whose `summary.failed` is above 0 while `failures` is empty is refused, for a unit run and the sweep. The sweep directive's `sweep` object shows the path, open and unowned deferred failures, units reopened earlier, declared baseline tests, the deferred-regressions record and owner decisions before approval. A blocked sweep report that brings a fresh `regression.json` reopens each owning unit (`red`, its `build-and-verify` step cleared, a `reopened` row, audit `unit.reopened`), so `orchestrate next` runs those units again before the sweep; unowned failures keep the sweep `red` and are listed in the next sweep's `stage.rework` with a hint. A stale file on a blocked sweep is ignored with a warning.
- The approved sweep's report output and `gate.decided` audit row gain `ownerDecisions`, `deferredRegressions` and `sweepRun` (`commands`, `baselineFailures`); the `complete` payload of a ledger intent gains `units`, `ownerDecisions` and `deferredRegressions`. `doctor` warns about deferred failures whose owning unit has not started and about unowned failures that will block the sweep. Open deferred failures of a unit that a design rework removes become unowned.

- `doctor` gains early warnings on intents with work units (the stored ledger, or the preview of the one the next command would build): a dependency that may be inverted (a unit already has finished work while a unit it depends on has none), a unit listed before one of its dependencies, registered `TS-` tests that no work unit owns, no declared test ownership at all, more work units than `unitSplitThreshold` with suggested waves (dependency levels, at most the threshold per wave), each parked unit with its kind, time and reason, a park that waits on a unit that depends on or waits for the parked unit, owner decisions recorded by the AI orchestrator that await confirmation, and a ledger that an older dtech-aidlc changed and the next orchestrate command will re-sync, and the `priorResults` a 1.0.0 whole-intent rework reset before the migration (information only; those steps run again).
- The `red-tests` directive of the first unit keeps its split-threshold warning and adds "Suggested waves of at most N units: 1) ...; 2) ...". The `unit` object of a unit directive gains `commands` with the `orchestrate report --unit`, `orchestrate park --unit` and `orchestrate queue` lines for that unit.
- Methodology: `phases/develop.md` describes work-unit scheduling (dependency order, the blocked kinds and `orchestrate park`, auto-park, the stalled hold, attributed regression with `regression.json`, the final sweep that carries the release-candidate gate, and scoped rework and split). `builder-verifier` writes `regression.json` and parks units instead of repeating a block; `implementation-planner` and the work-units template list each unit's owned `tests`, keep `dependsOn` honest instead of inverting it to reorder work, and change only the named units on a scoped rework; the test-strategy template gains a work unit to test mapping that `work-units.json` mirrors. The methodology README and contracts mention parks, attribution, the sweep and `intent rework --unit`.
- Harness skills (Claude Code and DeepSeek Harness) explain `--unit` on reports, `regression.json`, `orchestrate park`, `queue` and `revisit`, auto-parks, the `queue-stalled` hold (exit status 3), owner decisions (never revisited without the owner in human mode; recorded as unconfirmed in AI mode), `intent rework --unit` and `intent split`, and the final sweep. Projects projected by 1.0.0 show the skill as behind the engine; run `dtech-aidlc harness refresh`. The 1.0.0 hashes of the changed skill and methodology files are added to `core/data/projection-history.json`.

## 1.0.0

- The `dtech-aidlc` CLI is a native Rust executable installed with `cargo install --path . --locked --bin dtech-aidlc`. Every command (onboard/init, orchestrate next/report, status, scope, intent, config, harness, knowledge, ids, repos, deps, doctor, completion) runs natively, and the graph, methodology, harness projections and scaffold are embedded in the binary.
- The Node.js CLI (`core/tools/`), the npm package (`package.json`, `package-lock.json`), the Node test suite (`tests/*.mjs`, `scripts/lint.mjs`) and the Node installers (`scripts/install.sh`, `scripts/install.ps1`) are removed; Node is no longer needed to build, test or run dtech-aidlc. Upgrade and uninstall with `cargo install --force` and `cargo uninstall dtech-aidlc`, and delete an old Node installation by hand (see the README). Parity with earlier releases is guarded by golden snapshots under `tests/golden/`, recorded from the Node CLI with 0.7.2-equivalent behaviour; the methodology lint and repository checks are Rust tests in `tests/repo_content.rs`.
- Without `DTECH_AIDLC_HOME`, the embedded methodology is written to `.aidlc/engine/` (git-ignored, refreshed when the binary changes), and directive paths point there.
- Commands that write state now check that `.aidlc/audit.jsonl` can be written before changing anything.
- Known differences from Node: harness files always come from the embedded copies; some symlinked or dangling state paths are refused where Node writes through them; a prerequisite without a check command reports a readable error. Parity was verified on Windows only.

## 0.7.0

Changes from the backup-restore pilot review.

- The directive now returns `contractsFile` (the skills already told agents to read it, but it was never returned), a `template` path on each artifact that has one, `suggestedBranch` (`feature/<intentId>`), and `gateMode`.
- `implementation-design` produces two data outputs listed in the directive's `artifacts`: `work-units.json` and `ids.json`. Reporting the stage fails when either is missing or invalid: unit ids must be `WU-NN` (legacy `U-NN` is still read), unique, with `dependsOn` naming known units and no cycles. Previously a missing `work-units.json` quietly ran Develop as one implicit unit. Graph schema is 1.5.0, with a `data` output kind and a `template` key on outputs.
- ID registry: `ids.json` registers `FN-`, `IF-`, `TS-`, `WU-` and `CFG-` identifiers. `orchestrate report` refuses a Develop or Launch stage whose Markdown cites an identifier that is not registered, or an `AC-`/`US-` identifier that Analyze did not define. New `dtech-aidlc ids check [--stage ID]` lists them, plus registered functions no green verification report cites.
- Named prerequisites: `dtech-aidlc config prerequisite set NAME --check CMD [--hint TEXT] [--applies-to STAGE|PHASE]...`, `remove`, `check`. `orchestrate report --result blocked --needs NAME` records the blocker; `orchestrate next` re-runs its check and, while it fails, returns `blocked: true` with the `needs` list and exits with status 3 instead of re-selecting the stage. `--applies-to` makes a check a preflight before matching stages. The owner can override with `orchestrate next --force-resume --detail TEXT`, which is audited. `doctor` reports each prerequisite.
- AI-mode gates count deferrals: `gate-recommendation.md` needs an `## Open items` section whose items are tagged `[written-approval]` or `[follow-up]`, or `- None`. Any `[written-approval]` item, an untagged item, or a missing section refuses the AI approval. `gate.decided` records the counts.
- `dtech-aidlc config gate-mode GATE human|default` pins a gate to human approval inside AI-mode intents. A gate can never be pinned to AI approval.
- The `PROJECT.md` scaffold gains Commands, Environment prerequisites, and Known baseline failures sections. The directive warns while `PROJECT.md` is still the unedited scaffold, and in Develop when those sections are empty.
- Repeating Develop directives carry `context.baseline` (one baseline file per intent), and the first `red-tests` directive warns when the plan has more work units than `unitSplitThreshold` (default 6).
- Skills: one dynamic workflow per stage directive in AI mode (was one per phase); delegates are briefed with the directive JSON and the phase, agent, contracts and template files rather than a summary; writers cite registered identifiers and never mint them; environment check on the first turn of any stage that runs code; red first for fixes; depth proposal recommends `standard` for pilots and splitting unrelated work.
- Agents: `builder-verifier` checks the environment first, records the baseline once per intent, writes compiling stubs in compiled languages (a compile error is not red evidence), formats new tests before the red run, and applies red first to rework. `implementation-planner` mints and registers identifiers and recommends splitting oversized intents.

## 0.6.4

- The CLI starts again: 0.6.3 removed `model:` from agent Markdown while graph validation still required it, so every command failed with "agent ... id, phase, or model disagrees with Markdown". `phase-graph.json` is now the only source of an agent's model alias, and agent Markdown that declares `model:` is rejected.
- `red-tests` and `build-and-verify` now run once per work unit for every unit in `work-units.json`, in order. Previously only the first unit ran and the intent was reported complete without the rest.
- The release-candidate gate is presented once, on the last work unit's `build-and-verify`. Earlier units report without `--approval`, and their directives carry `stage.phaseGate: false`; passing `--approval` on them is refused.

## 0.6.0

- Human gates and material unknowns are presented with direct AskUserQuestion calls: the question names the gate, criteria, and artifacts; options state consequences with the recommendation first and marked `(Recommended)`; `Other` free text is treated as the decision. Skipping a question is never approval.
- Intents run in an orchestration mode: `human` (default, the owner approves every phase gate) or `ai` (the AI orchestrator researches each gate, records a `gate-recommendation.md`, and approves as `"AI Orchestrator"`). Set the project default with `dtech-aidlc config mode ai|human`; override per intent with `orchestrate next --mode`. Directives carry `mode` and `orchestrationMode`; `intent list` and `status` show the mode; the `gate.decided` audit row and `state.gates` record `mode` alongside the approver. The CLI rejects human approver names in AI mode, rejects `"AI Orchestrator"` in human mode, and refuses AI gate approval without a non-empty `gate-recommendation.md`.

## 0.4.0

- `install.sh` adds `--upgrade` (replace in place, repair a partial installation, roll back on failure) and `--uninstall`. A plain re-install fails with one line that names all three installed paths. The launcher resolves symbolic links and fails with one line (`installation is incomplete`) when the library is missing. Files that are not dtech-aidlc files are never replaced or removed.
- A project that uses only the DeepSeek harness no longer gets `stage.model` and `stage.modelSource` in `orchestrate next` or a `model` in `scope NAME`; `config agents` shows source `unsupported`, and `config agents set` is refused (claude harness only). Harness manifests declare `modelAliases`.
- `repos pull` follows the remote's default branch for a dependency registered without `--ref`, instead of whichever branch was fetched first.
- `npm run lint` checks that the methodology README's scope lists, agent roster, phase sections and gate ids agree with the graph. The README now has an Archived section and gate ids, and its approval-record fields match the CLI's audit row.
- The root README describes onboarding, project knowledge, what to commit, harnesses, upgrade and uninstall, and environment variables.

## 0.3.0

- Existing documentation is registered by reference in `aidlc.knowledge.json`; BRD files are no longer copied into `.aidlc/shared/brd`, and the `brd` key is removed from `onboard` output and the project profile. Existing copies are left in place and may be deleted.
- `onboard` adds `--docs`, `--no-detect` and `--rescan`; it creates `aidlc.knowledge.json` only when it registers at least one document.
- `init` is an alias of `onboard`; it scans the project, writes `.aidlc/shared/`, and creates a root `aidlc.knowledge.json` when documentation is detected or supplied with `--docs`.
- The project profile is schema version 2, marked generated, and supports the `unknown` project kind. Folders such as `vendor`, `target`, `out`, `obj` and `venv` are excluded from source evidence, and `.kt` files are reported as Kotlin.
- `orchestrate next` directives add `context.profile.kind`, `context.sourceChanges` and `context.codebaseMap`, with warnings for missing or changed registered sources. `doctor` adds a `Knowledge sources:` check.
- The methodology adds the one-time codebase map at `.aidlc/knowledge/_codebase-map.md` and brownfield guidance for Analyze, Ideate and Develop.
- `build-and-verify` requires a fourth output, `regression-report`; intents that have not completed that stage must write it.
- A new project must choose `--harness` on its first `init` or `onboard`; existing projects can add a harness with `harness add`, and `config scope` shows or changes the default scope for new intents.
- Decisions are written once in the decision record; the architecture design only lists them.
- State migrates by itself; run `dtech-aidlc harness refresh` for the skill files and `dtech-aidlc onboard` for PROJECT.md, the manifest and the profile.

## 0.2.0

- State version 2: `.aidlc/state.json` is a pointer and each intent has its own state file. Intents run one after another, with `intent list`, `pause`, `resume` and `abandon`.
- A phase gate cannot be passed without a recorded approval that names the approver, and a stage cannot be reported complete until every file it produces exists at the path the directive lists.
- Project knowledge: `PROJECT.md`, `aidlc.knowledge.json`, the knowledge house `.aidlc/knowledge/` with one record per closed intent, the `knowledge` commands, and a `context` object in the `orchestrate next` directive.
- Harness manifests are JSON data files and projected skill files carry a `.projection.json` stamp. `harness status`, `harness refresh` and `harness add` are new, and `doctor` checks the projection.
- The methodology is no longer copied into projects; the CLI reads it from the installation (see `DTECH_AIDLC_HOME`).
- `--intent-file` and standard input supply the intent text.
